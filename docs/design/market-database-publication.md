# 市场数据库分离与版本发布

状态：设计已确认，版本化实现已通过人工代码审阅与本地验证。线上已部署的旧版仍使用[副本差量发布](ingestion-replica-plan.md)。实施范围为一次完整的存储与发布替换；设计确认、代码审阅、生产切换分别进行。

## 决策与依据

应用数据持续原地写入；市场数据按版本读取。采集和修复只写一个工作版本。审核通过后，把这个已经建好索引的市场库设为当前版本。首次采集、正常日更、长时间停采后的补齐使用同一条发布路径，发布操作不按变更行数分支。

11 月 14 日生产 Run `01M7AV1RNM1NXF95R4WZBZY6TC` 产生约 21 GiB 混合候选库。11 月 15 日接受时，日志记录 76,417,066 项市场变化，仅准备清单就耗时约 4 小时 50 分钟。取得发布锁仅约 6 ms；随后在 30 分钟回退预算下写入 Daily 时，Prisma 报事务失效。错误信息不足以确定事务关闭的精确原因。采样时进程内存峰值约 424 MiB。此次观测支持消除逐键比较和二次插入，并不能用来估计普通日更的写入量。

长期成本移到两个可独立测量的步骤：生成可写候选，以及采集、验证数据本身。发布只需封存完毕的文件和一个短应用库事务。若文件系统不支持块共享，每轮建立候选仍有一次完整市场库复制的开销；同时保留上版时，须预算最多三份库、活动 WAL、迁移临时空间和备份。

## 数据归属与布局

沿用现有应用库路径和认证连接配置。市场库目录与应用库同机，路径示意如下：

    /var/lib/jixie/prod.db                         应用数据、发布控制
    /var/lib/jixie/market/versions/<id>/market.db  从候选创建到发布使用同一路径
    /var/lib/jixie/market/locks/<id>.lock          该版本的跨进程读者锁

版本 ID 独立于文件内容摘要；普通采集以 Run ID 生成唯一目录，初始基线与迁移基线也有独立 ID。只接受应用生成的 ID，按固定根目录解析路径。当前版本的唯一依据是应用库的一行指针。API、Worker、CLI 均通过同一解析入口打开版本。禁止用“最新目录”、进程启动时的默认连接或单独更新的符号链接推断当前版本。

| 归属 | 表和职责 |
| --- | --- |
| 应用库 | User、Session、InviteCode、EmailLoginChallenge；Factor、Strategy、各报告、Job；Research 文档、Cell、执行、产物、提案；Agent 会话、消息、运行。供应商能力探测 TushareCapabilityProbe 是运维记录，也留在此库。 |

两套 Prisma 6 schema、各自生成的客户端和迁移历史。应用代码显式取应用客户端；市场读写入口分别取当前读取作用域或有所有权的候选客户端。消费者跨库关联用已有业务标识，在应用层组合；应用库内的授权、Job 和结果事务继续在一个库中完成。按 Prisma model 枚举检查归属，新增 model 必须归入一侧。禁止从市场读取路径隐式创建空库、迁移或开启写 WAL；用驱动实际支持的只读连接配置并在集成测试中证明写入被拒绝。

## 连接取得与只读边界

当前默认 Prisma 实例由模块创建，业务用 `getDatabase()` 从 `withDatabase()` 绑定的 AsyncLocalStorage 取连接；旧 `withCandidate()` 临时替换同一个槽位。拆分后应用和市场分别绑定，进入市场作用域不得覆盖应用连接。回测结果写入应用库，选股、K 线及复权数据在同一任务的市场版本中读取。Worker 跨进程只传版本 ID，在子进程解析并持锁。两套客户端分别生成，schema 和迁移也分开。

应用库按既有授权读写。采集、补录仅能取得可写候选连接。封存时排空候选连接并校验 checkpoint；发布版本和仍有读者的旧版本用只读连接打开，不执行写 WAL 初始化，不创建缺失数据库。访问权限靠连接和文件共同约束，不能仅靠隐藏某几个 Prisma 写方法。状态、诊断查询也需选对源，当前候选与已发布历史不得混读。

| 现有锁或新锁 | 用途和持有时间 |
| --- | --- |
| maintenance.lock（保留） | 串行化创建候选、采集、修复、接受、拒绝及回收。 |
| market-access.lock（保留） | 获取当前版本、锁定并打开文件期间读者持共享锁；切换指针与回收判定期间持排他锁。普通发布不等待旧版长任务退出。 |
| market-publish-intent.lock（退出普通发布路径） | 仅部署／schema 迁移在需要排空全应用时使用。部署排空另须等待已持有版本锁的任务释放，避免把短锁误当成长期读者屏障。 |
| 每版本文件锁（新增） | 读者持共享锁到连接关闭；回收者持独占锁。版本文件清除与新读者打开受同一顺序保护。 |
| owner-*（保留） | 约束后台任务的执行权，不兼任市场版本引用。 |

## 一轮采集、修复与接受

1. **创建。** 在应用库登记父版本、目标日期和候选执行权。首次从空市场 schema 初始化。已有版本从封存的父库创建独立可写文件；优先在目标卷验证并使用 reflink，普通 SQLite 一致备份为受支持的回退。禁止硬链接。先在临时文件完成并校验，再安装到版本目录、标记就绪。克隆中断只清理未就绪产物。记录复制方式、字节与耗时，空间不足在采集前报错。
2. **采集与修复。** 批次、业务值、问题和候选修订继续同事务提交。retry 恢复相同工作版本并跳过成功收据；repair 继续要求计划预览和哈希。候选客户端关闭并不代表采集完成。应用库阶段更新晚于市场库终态时，recover 从 Run 结果重建控制状态；未确定旧进程退出时维持既有执行权约束。
3. **封存。** accept 持维护写者锁，重新核对操作权、父版本、名单版本、审核哈希和 pending／review。排空该候选的客户端，完成 WAL checkpoint 并检查返回值，切回可独立打开的单文件模式，关闭最后写连接。核对文件身份、schema、Run 与修订，持久化文件和目录。完整性检查在切指针之前执行，耗时单列。封存后禁止写入。若切换前失败，可重验同一文件继续；需要再修复时必须显式解除封存、使旧审核版本失效。
4. **发布。** 在应用库同一个事务内比较父版本和操作 token，写入当前版本 ID、发布序号和本次发布凭据。该事务提交是唯一对外生效点。重复 accept 返回相同凭据。失败仍可读取旧版；提交后进程崩溃只补收尾。此步骤不打开市场写事务，不遍历行情行、不重建索引。
5. **拒绝与清理。** reject 保留拒绝原因和控制记录，按现有拒绝副本策略清理候选。回收与发布解耦，回收失败可重试。保留当前及上一已发布文件，并保留所有仍被使用或显式要求留存的版本；控制凭据长期保留。回退到上一版需显式管理员操作，创建新的发布序号和回退凭据。用户操作、Job 和报告继续留在应用库。

跨文件不要求原子提交两份 SQLite 数据库：先使市场文件可独立恢复，再提交应用库指针。若进程死在两步之间，文件可识别、指针仍指旧版。启动发现指向的文件缺失或损坏，明确报错并走恢复，禁止静默挑另一个文件。

## 长任务与旧版本回收

每次 HTTP 市场查询、一次 Research 执行、一次因子分析或完整策略回测只绑定一个版本；多次 SDK 调用和子 Worker 显式传递该 ID。普通新请求从应用库解析当前版，排队 Job 在约定的输入冻结点记录版本 ID（提交时冻结输入的 Job 就在提交时固定）。未启动和可恢复的 Job 也构成保留引用。缓存键包含市场版本 ID，业务报告记载其输入版本；历史报告读取已保存结果，精确重跑所需旧版通过显式保留或备份恢复，不承诺无限保存所有数据库文件。

用现有跨进程文件锁机制处理“刚读到指针、文件却被回收”的竞态。解析当前版、取得该版本共享锁并打开文件期间，持短期全局读锁；发布切指针或 GC 决定回收时持对应排他锁。读取任务只在打开期间占全局锁，此后持版本锁至最后一次读取及连接关闭。GC 再核对当前版、回退版和持久 Job 引用，尝试取得独占版本锁，获取失败即延后。锁顺序统一为维护锁（写者如需）→ 全局锁 → 版本锁，读者不反向申请。进程退出由 OS 释放锁。避免用长生命周期 Prisma 连接池永久固定旧文件。

## 当前生产候选如何接入

专用迁移入口默认预览，实际转换需显式执行。**不得通过旧 bootstrap 的业务 reset 来完成此次拆库。** 旧 reset 与重建标记在部署路径中必须与本次迁移互斥，发现未完成的旧重建先停下报告状态。

- 停采集计时器，确认没有采集、修复、发布和其他写者；安排维护窗口，备份旧主库、所有未决候选和必要的配置，验证可恢复并预检空间。保留旧库原件，所有转换先写新路径。
- 从切换时的主库提取应用表，保留用户私有数据、主键、关联及相关文件路径。用主库当时可见的市场数据建立**已发布基线**。当前生产主库若仍是 revision 0，就保持空基线；一般部署若已有非空市场数据，同一转换程序保留该基线。
- 将未决候选中的市场表、修正证据、名单、Run／批次／问题／处理结论完整转成市场版本，排除用户表和旧变更日志。只读源、按明确列在 SQLite 内批量复制，必要时重建目标索引。保留原 Run ID、目标、字段精度和时间语义。转换可能复制大量数据，这是一次性成本，要实测。先验证旧父基线和发布凭据；版本或状态不一致时停止。已关闭进程的中断 Run 保留恢复能力，不能自动升级成已审核。
- 生产 Run `01M7AV1RNM1NXF95R4WZBZY6TC` 在最近核验时为 awaiting_publish；按实际迁移时状态导入。若仍待发布，保留修复结果、导出新审核版本供复核，由维护者单独 accept。迁移不触发重采或自动批准。若已发布则按凭据导入，禁止重复发布。
- 在隔离路径完成表计数、分表摘要、关键业务键、认证和私有数据摘要、SQLite 完整性与外键核验，并确认市场版本 schema 中不含用户表。两套新库及指针一致后才切服务配置，重启所有客户端。迁移失败或切换前中断可从原件重试；新系统开放写入后，要回退整个应用必须先处理新增用户写入，不能把旧主库直接盖回去。

## 运维、兼容与验收

现有 ingest、runs inspect/retry/accept/reject/recover、issues export/repair 及 Web 审核操作继续按 Run ID 使用。状态接口分别报告候选采集／封存／切换和当前已发布版；日志给出文件大小、复制／校验／等锁／切换耗时。阶段没有可靠分母时显示阶段与耗时。Research SDK 的公开方法及行情数据契约保持；前端和双语帮助只在状态语义变化处同步。发布不会把工作版本暴露给普通用户。

备份以一份清单绑定一致的应用库备份、当时指向的不可变市场文件及可恢复的候选；备份期间固定版本，候选采用已有写者协调或在线备份。恢复先验文件／schema 和版本引用，再开放服务。SQLite 自由页不会自动释放磁盘，使用实际占用核算。磁盘预算同时考虑主库、旧版、候选及验证备份，未决候选和当前版不能作为腾空间目标。

实现主要影响 API Prisma、infra/database、infra/coordination、market、ingestion、Research/Factor/Strategy 的宿主取数和 Worker、管理员 CLI、部署／备份脚本及说明文档。保留单 VPS、SQLite 和 Prisma；不引入集群或逐行版本表。部署需配套更新 Prisma 生成、迁移、版本目录权限、systemd 可写路径和部署影响测试。分库后误用客户端应在类型或边界检查阶段被发现。

| 必验场景 | 判定标准 |
| --- | --- |
| 首次、日更、长期停采后集中补齐 | 同一 accept 路径；记录候选生成、封存校验和切换的独立耗时及磁盘峰值；切换阶段没有随变更行数增长的 SQL 或文件复制。 |
| 并发读写 | 切换中持续提交用户操作均保留；跨切换运行的回测／多 Cell 执行只读原版本，新请求读新版。排队、Worker 重启、版本回收相互不丢引用。 |
| 故障与重入 | 对复制、checkpoint、文件持久化、指针事务提交前后、回收分别注入失败；并发 accept、基线变化、重复执行均得到唯一可核查结果。 |
| 采集语义 | 修复后的两条数据／结论、未知与历史诊断、增量成功收据、名单增删及下载范围在转换前后对齐。 |
| 生产规模演练 | 使用生产备份与候选的隔离副本，证明 7,600 万级变化无需再次逐行发布；记录冷启动、正常增量、集中补齐的复制与可用性成本。实际发布和生产迁移另行安排。 |

## 本地十年跨度验证

1. **补采语义**：两个独立临时目录，分别将应用库、版本根目录、锁、备份和来源配额路径绑定在测试目录。用可控来源按 `20161116` 经正常 ingest、审核、accept 建立基线；同一来源随后提供到 `20261114` 的交易日、换码、新上市、跨期财报修订及分红。验证增量计划复用旧成功收据，修订按实际披露时间接纳。用另一套空库从头采到同一目标，对照自然业务键、值和 PIT 可得时间；捕获时间与随机 ID 按血缘单独核验。这个合成历史只用于功能验收。
2. **大批发布**：使用 SQLite 在线一致备份取得当前工作库快照（活动 WAL 有未 checkpoint 的内容，不能只复制 dev.db），通过迁移程序把市场数据转换为隔离候选。用小规模旧基线与大候选验证正式版本切换、长读与回收，并记录全量复制／校验时间及 accept 锁内 SQL 次数。后者是发布压力试验，不宣称模拟了十年前真实可知的全市场历史。
3. **真实历史回放**：若有当时留下的完整快照，应同时恢复市场数据、收据、名单和 scopeSnapshot。只有今天的库时，按日期删除新行情会留下今天的目录、历史修订和成功收据，无法复原十年前的知识状态。精确历史不可得时保留这一局限。所有测试只在代码审阅后执行，磁盘空间按各副本和 WAL 的实际需求预检。

压力样本准备入口为 `apps/api/scripts/prepare-market-fixture.mjs`。输入为隔离的一致备份和一个尚不存在的输出目录；默认只打印目标路径，显式 `--apply` 才构建市场样本。输入以只读方式挂载，输出使用独立市场 schema，按列、行数、外键与 SQLite quick_check 核验。该工具保留快照里的数据与收据，只用于制造近当期的大候选，不能把它作为十年前的已发布基线。

## 审阅与交付

建议开发提交信息：`feat(ingestion): publish reviewed market database versions`。交付为同一项完整功能，含存储边界、迁移、发布、消费端、备份恢复和相关测试。设计确认后按 review-gated-development 实施：先完成代码和静态检查（格式、lint、类型、后端边界、生成物一致性、迁移与脚本静态审查），交人工代码审阅；审阅通过后执行约定的行为测试、隔离迁移与回滚演练、构建及适用的界面验证。通过后按约定提交，不自动 push 或操作生产。

## 实现与审阅入口

- `prisma/app` 和 `prisma/market` 各自生成 Prisma 客户端并维护迁移历史。原 `prisma/schema.prisma` 与旧差量读写实现暂留作混合格式兼容及迁移对照。bootstrap 检测旧布局后要求离线转换，分库状态存在时所有新版 accept 只走指针事务。应用库缺少指针时应报错。
- `src/ingestion/version-collection.ts`、`version-lifecycle.ts`、`version-publication.ts` 分别负责候选准备／续跑、核验与接受、封存后的切换和回收。`src/infra/database/market-database.ts` 与 `src/infra/coordination/market-access.ts` 绑定实际版本。文件不可写、连接只读和版本锁分别保障不同边界。
- 转换、备份与恢复参见[部署说明](../deployment.md#切换到独立市场版本库)。转换产生新目录；维护窗口内才可替换部署配置。回收时若新分支缺少旧 Run 收据，保留原文件以支持历史诊断。
- `version-gap.integration.test.ts` 用 ETF 合成来源在两个独立临时布局对照，比较 2016 → 2026 补采与直接采至 2026 的结果。`version-migration.integration.test.ts` 覆盖移交既有候选、候选创建后的应用写入、备份恢复和正式 CLI 接受；`version-publication.integration.test.ts` 覆盖封存只读、切换和固定旧读者。实测时间及生产规模结果留待审阅后补录。
