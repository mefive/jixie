# Ingestion 数据采集设计

Ingestion 按目标日期推进。主库保存每轮运行及发布状态，采集、核验和修复在同一 Run 的工作副本进行。维护者接收后，候选差量一次发布到主库。状态切换、恢复和发布协调见 [副本采集设计](ingestion-replica-plan.md)。

## 职责与范围

主流程为 **创建工作副本 → 确定范围 → 下载、校验与写入 → 核验与修复 → 接收发布**。

Ingestion 不承担指标计算、入库后的质量审计或部署。指标计算独立处理；若提供前端按钮，生产环境由后端校验管理员身份，开发环境可通过服务端配置跳过。

调用语义为 `ingest(T)`：补齐采集范围内从自然起点到目标日期 T 的数据，不提供单独的起点参数，也不设置每天、每周等内部刷新频率。外部定时器只负责决定何时调用。

股票保留上市、退市和暂停上市标的；ETF、指数按累计下载名单采集。ETF 每轮按历史日期自动补充，空名单也继续选取；指数只初始化缺失配置，保留已保存的空名单和人工修改。

2026-11-03 删除财务目录扫描并建立 1988 年起的批量采集范围，历次策略和验收见下方开发记录。

## 自然起点与批次

“全量”指所选市场、标的及已约定覆盖范围内的有效历史；财报与财务指标只覆盖 1988 年起的季度。

| 数据 | 自然起点 | 采集单元 |
| --- | --- | --- |
| 交易日历 | 相应市场所需的历史起点 | 交易所＋年份 |
| 股票、ETF 基础资料 | 来源提供的目录 | 目录或上市状态快照 |
| 股票行情、复权、估值、限价 | 当前市场的有效上市日 | 各自接口＋交易日 |
| ETF 行情、复权 | 当前市场的有效上市日 | 各自接口＋证券＋年份 |
| 指数行情、官方估值 | 各自来源的历史序列起点 | 各自接口＋指数＋年份 |
| 历史名称、指数成分 | 来源可提供的最早相关历史 | 名称按年，成分按指数＋月 |
| 三张财报 | 固定 1988 年，不采更早报告期 | 首次和增量按种类＋报告类型＋公告日期区间，缺少覆盖时补实际公告日或证券历史 |
| 财务指标 | 固定 1988 年 | 按季度获取全市场 VIP 数据 |
| 分红 | 来源可提供的全部历史 | 首次按证券补完整历史，之后按自然日分别采公告日和实施公告日 |

同市场换代码接续历史；跨市场行情从实际进入当前市场之日起计算，不拼接前市场行情。公司财务历史不因转市场自动截断，也不因行情截断而自动套用 IPO 交易规则。

来源历史可能短于标的上市历史。无法取得或确认的范围必须说明，不能以本地最早一行证明此前已采齐。目录、分红等快照反映抓取时刻，不冒充目标日的历史快照。

## 四张采集表

行情、目录、财报等继续使用各自业务表。Ingestion 只保存以下执行信息；日期和时间分别表达业务范围与实际捕获时刻。

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| `IngestionRun` | `id`、`trigger`、`targetDate`、`scopeSnapshot`、`status`、`startedAt`、`finishedAt`、`summary` | 一轮目标、范围与结果；摘要不承担恢复游标 |
| `IngestionBatch` | `id`、`runId`、`dataset`、`scope`、`period`、`api`、`request`、`rangeStart`、`rangeEnd`、`sourceStart`、`status`、`responseComplete`、收取／接纳／过滤／未接纳数量、开始／结束时间 | 一个采集单元的一次实际尝试 |
| `IngestionIssue` | `id`、`runId`、`batchId`、`category`、`severity`、`reasonCode`、`message`、`businessKey`、`field`、`payload`、`createdAt` | 请求失败、受阻原因、未接纳错误和来源警告 |
| `IngestionSelection` | `assetType`、`codes`、`updatedAt` | ETF、指数下载名单；`assetType` 为主键 |

前三张表使用独立 ID；批次关联运行，问题关联运行及可选批次。`dataset＋scope＋period` 标识逻辑单元，一次进程调用最多尝试一次；恢复同一 Run 时为未完成单元创建新的批次记录。索引允许保留同一单元的多次尝试，成功尝试与旧诊断均不改写。日期型批次记录实际请求范围，按范围判断已有成功是否覆盖本次需要，不能把未结束年度当成全年完成。

采集执行状态为 `running / completed / completed_with_issues / interrupted / failed`。批次状态为 `running / succeeded / partial / failed / interrupted`。`succeeded` 表示来源响应完整且应接纳内容全部处理成功。副本的修复和发布进度由独立的生命周期状态记录。

成功批次本身就是恢复依据，不另建分区状态表、连续水位表或全局数据就绪资格。最近失败不修改过去的成功事实。未完成 Run 的成功明细始终保留；已完成运行保留最近 20 轮明细，较早批次只在已有更新成功收据完整覆盖时压缩；恢复所需收据、所有问题及关联批次保留，运行摘要按当前计划各单元的最近尝试重建，旧问题保留历史但不重复作为已修复故障报告。阶段计划保存在 Run 快照，不预写批次队列表。Market 保留数据修订号，用于研究会话和缓存失效；修订号不表示采集覆盖。

## 一轮同步

1. 固定目标日期 T，通过主库事务占用唯一活跃名额并建立工作副本。同一目标的中断 Run 可以继续使用原副本、开始时间和阶段计划。候选副本由维护者接收或拒绝后释放名额。
2. 准备必要的日历和基础资料。区分最终目标 D 与历史循环日期 t：对每个不晚于 D 的已结束开市日 t，使用 t 当日规模选取最多 100 只 ETF，与已有名单取并集；每个日期独立提交名单与收据，完成后固定本轮累计范围。当前已退市的 ETF 可参加退市前排名，不用今天的规模或上市状态回填历史。不足 100 或完整无记录均正常，不补零、不改用份额。指数保留原名单策略。前置失败只阻止真正依赖它的部分；行情、复权、估值、限价之间没有采集依赖。股票仅按交易所日历中已知开市日生成单元；上市日期早于日历可得范围是正常历史缺失，不补自然日、不报错。SSE、SZSE、BSE 各用自己的日历，不借用其他交易所的日期；同日一次请求返回多个交易所数据时，只接纳当日本所日历明确开市的记录。
3. 股票目录完整后，三张财报按接口和报表类型 1／4／5 扫描公告日区间，根据完整收据补实际公告日和未覆盖证券。Run 保存证券范围与计划，收据保存每次请求及完整响应。财务指标按季度调用 fina_indicator_vip，完整空响应正常成功。
4. 恢复时跳过本 Run 所有已成功单元，包括基础资料、财报、指标、分红和名称；只重试失败、partial、中断与未尝试单元。新 Run 才重新获取这些可更新来源。历史行情继续允许复用其他 Run 的成功范围收据。ETF 选取等前置重试补入新标的后，补充相应历史计划。
5. 数据集与对象轮换，近期新增数据和历史缺口交替推进。每个单元本轮最多尝试一次，直到没有可执行工作或被取消；单请求保留超时、限流与有限重试。
6. 汇总成功、过滤、未接纳、失败及受阻情况。采集完成后根据待处理问题进入待修复或待发布，由维护者核验和接收。发布时用发布锁协调正在使用主库的业务请求和任务。

每次推进后，按 `IngestionBatch.startedAt` 和 `finishedAt` 保存本轮每次实际尝试的起止时间与耗时，并按数据集汇总。复用的历史收据计入覆盖范围，单独报告整轮实际用时。

日行情只请求已经结束的交易日；日历允许为可得日定位而有限前瞻。来源尚未发布的数据不能被承诺已取得。

## 批次提交与断点恢复

**整批下载完整响应，包括全部分页，再提交业务数据。** 可以提前保存执行中记录，网络期间不持数据库写事务，也不逐页提交业务数据。

转换结束后，在副本的同一事务内提交合法业务数据、未接纳问题、批次结果及实际数据变化对应的修订号。

| 情况 | 处理 |
| --- | --- |
| 下载失败或分页截断 | 本次不写业务数据，保存失败原因 |
| 完整响应含个别无法接纳的独立记录 | 合法记录和 error 一起提交，批次为 `partial` |
| 正值且有限的 OHLC 存在范围矛盾 | 原值与 warning 同事务保存；无其他错误时批次仍成功 |
| 成分快照等完整对象无法接纳 | 该对象不替换旧值，其他独立对象继续处理 |
| 下载、转换期间被强杀 | 没有本次业务提交，重启后整批重试 |
| 提交事务期间被强杀 | 数据库保证全部提交或全部回滚 |
| 提交后、运行汇总前被强杀 | 业务数据与批次结果都存在，恢复时保留成功 |

重试使用业务键和明确的更新／追加规则保证幂等，无须先清理上次合法数据。数据库不可写等基础设施故障停止本轮；无法保存问题时先输出进程日志，恢复后识别遗留的执行中状态。普通数据或请求问题不终止其他独立单元。

## 接纳与问题记录

信任 Tushare 的数据含义。每类数据只明确三件事：**是否属于范围、能否准确解释、应当如何保存**。校验响应结构、完整分页、必要身份和字段，以及业务键是否可无歧义保存，不额外推断数据“应该长什么样”。

- 负 PE、允许的 null、来源的零限价按字段含义保留；来源无记录不自行解释为停牌，不补零、不生成价格。
- 上市日晚于本轮截止日的标的先正常过滤，不因范围外缺字段报错；上市当天纳入，已上市公司的上市前财报仍可保存。其他范围外记录正常过滤；尚未适配的身份或分类与来源格式错误分别记录，不能统称为来源数据错误。
- 缺失字段、未知 null 与明确清空区分处理。失败、截断、来源缺席或单纯的当前目录变化，不授权擦除旧历史；完整快照的替换范围由该数据集约定。
- 财报版本、原始来源代码、公告日、捕获时间和可得时间分别保存；同值重抓不推迟首次捕获时间。

未接纳问题必须能定位接口、请求、业务键、原因和必要原始内容。请求和问题记录排除凭证。当前问题按最近一次相关尝试判断，诊断保留当时事实，处理结论由 `IngestionIssueResolution` 单独记录。详见 [问题处理与数据状态](ingestion-issue-resolution.md)。

## 来源更新

目录、名称和财务指标每个新 Run 重新获取一次，恢复未完成 Run 跳过已经成功的单元。财报按公告区间和实际公告日的成功收据补齐新增披露。分红复用逐股完整历史收据，补齐公告日与实施公告日。批次成功表示本次返回内容已处理，后续修订仍按其披露日期接纳。来源指纹、公告日、首次捕获时间和分红较新基准选择规则继续适用。

全市场财务下载先按本轮最终截止日判断证券是否已上市，再接纳 1988 年起目标范围内的季度报告；不用报告期作为上市准入截止日，避免丢失上市前财务历史。股票目录外以及上市日晚于目标日的证券不进入批量财务计划。

股票四类日数据保持每接口＋交易日的批次粒度。分页分别采用 daily／adj_factor／daily_basic 每页 6000、stk_limit 每页 5800；财报 VIP 每页 5000，指标 VIP 每页 10000。分红公告日查询每页 2000，逐股完整历史仍按快照查询。满页继续取下一页确认完整，不把刚好触及上限视为结束。请求继续串行，维持原 800ms 最小间隔。

旧版未完成 Run 在同一 ID 内建立阶段计划，保留原逐证券成功明细；这些收据不能冒充全市场某期已完成，新报告期批次首次仍需下载，业务表按原规则幂等接纳。无需清库、删除旧问题或迁移业务行。

## 财报按公告日期区间采集（2026-11-06）

提交为 `perf(ingestion): batch financial statements by announcement range`。人工代码审阅和验证均已通过。

三张财报首次和增量共用 `ann_date` 区间规划。从 1988 年起按月组织未覆盖日期，公告标签扫描延伸至规划当日，报告期和证券按本轮目标准入。单页达到上限即按日期二分，单日满页保留未完整诊断。请求和来源字段由成功收据复核。完整历史窗口从实际请求开始日判断何时可能出现此前未见的实际披露，同日保持待补，已成功的 `f_ann_date` 逐日收据按原口径复用。证券范围不足时定向补历史，含延后报告期的收据在目标推进后重新核对。

旧季度收据继续保留原报告期事实。显式重试中断候选时，一次性更新未完成财报计划，保留成功与有诊断的单元、数据及批次历史。同一副本继续核验发布。代码审阅后验证隔离库恢复、满页二分、失败原子性、实际公告日期边界、旧版收据、候选核验及只读真实来源对照。

首次审阅后，47 个测试文件共 265 项通过，完整构建通过。2022-08-27 至 08-29 的三张普通报表以区间查询加实际公告日补查得到相同的来源版本集合，计划请求数由 18 降至 12。2022 年第三季度的普通利润表用 7 次区间探测取得 6,479 行，数量与独立短窗口对照一致。暂停副本的只读拷贝试算显示，旧计划剩余 17,611 个财报批次，首次实现规划 10,236 批，其中 6,234 批为逐股历史。

根据上述试算调整证券范围不足的计划选择。批量重扫受影响的公告窗口预计需要更少计划单元时，优先用区间覆盖这些证券。否则沿用逐股补查。此处按计划单元估算，满页拆分会增加实际来源请求。

修订通过第二次人工审阅。47 个相关测试文件共 266 项通过，完整构建通过。新增隔离库用例验证一份窄名单收据会触发一个批量窗口重扫，从而覆盖两只原计划逐股补采的证券。旧的 `2022-10-01` 候选按维护者要求拒绝并清理，最新修订的选路通过隔离库验收。
