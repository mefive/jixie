# 设计：自然语言量化研究工作台

状态：实施中。M0–M2、M4、M5 已完成；M3“研究提升为因子”按产品决策暂缓。当前可复现研究记录已覆盖正式运行
历史、父子重跑、协议/实现/数据/环境指纹、字段级替代口径、结论变化归因和失败尝试。

## 1. 产品判断

jixie 的核心价值不是让用户在聊天框里间接编写 SQL、TypeScript 或 Python，而是让不懂编程、统计学基础
有限的用户，也能提出一个投资研究问题，并得到口径明确、方法适当、可以复核的统计结果与结论。

普通 Agent 可以搜索资料、临时写代码并解释一张表；本工作台的差异应来自一套受产品约束的研究过程：

1. 先把自然语言问题转成可以反驳的研究问题，而不是直接给答案；
2. 明确变量、样本、频率、滞后、基准、币种、数据可得时间和异常值处理；
3. 从版本化研究协议中选择方法，由系统执行经过测试的计算；
4. 同时展示结果、假设、诊断、稳定性、限制和结论强度；
5. 给出公式、变量解释、Python 示意代码和相关概念文档，让用户知道结果怎样得到；
6. 保存证据和版本，必要时把成熟研究显式提升为 Factor 或 Strategy。

一句话定义：**Agent 负责理解、规划和解释，平台负责数据、计算、约束和复现。**

## 2. 与因子研究的产品边界

通用研究以问题为中心，不要求问题最终产生预测信号。例如：

- 利率下降是否伴随成长股跑赢价值股；
- 黄金与股票的相关性是否在危机期间改变；
- 一次政策公告前后，某行业的收益、成交量和波动怎样变化；
- 两组股票的估值分布是否有实质差异；
- 某个组合的回撤主要来自哪些资产和时期。

因子研究以一个可发布的横截面预测信号为中心，必须冻结因子定义、方向、股票池、预测期限、探索样本，经过
正式报告、holdout、成本和发布流程。两者共享数据、统计方法和 Agent 基础设施，但拥有不同的结果对象和完成
定义，不能把两个入口合并成同一种报告。

### 2.1 一键转因子

通用研究过程中可以出现“适合转成因子”的建议卡，但不能由模型自动创建正式因子或直接揭示 holdout。

建议条件至少包括：

- 已形成可逐股票、逐时点计算的候选预测变量；
- 已明确未来收益目标、预测期限、预期方向和适用股票池；
- 数据覆盖和可得时间没有明显阻塞；
- 研究结果不只是同期相关或个别样本叙事；
- 参数和变换可以写成确定性的因子定义。

用户点击后只创建一个**私有因子草稿**，带入假设、变量定义、数据来源、参数、研究运行链接和已有证据。
因子 Agent 继续完成代码校验、正式报告、探索/holdout 与发布决策。建议卡应同时说明“已具备什么”和“还缺
什么”，而不是把相关性包装成预测能力。

## 3. 用户主流程

```text
自然语言问题
    ↓
问题形式化：变量、样本、频率、时间关系、基准与口径
    ↓
研究计划卡：拟用方法、关键假设、所需数据、可调整参数
    ↓ 用户确认歧义项
版本化研究协议执行
    ↓
互动图表 + 统计结果 + 诊断 + 结论强度
    ↓
公式 / Python 示意 / 概念文档 / 数据与运行记录
    ↓
继续追问、改参数后重跑，或显式提升为 Factor / Strategy
```

清楚且低风险的问题可以直接运行；会改变结论含义的歧义必须先确认。例如“利率下降”可能指政策利率变动、
十年期收益率的日变化或一个降息周期，系统不能静默替用户选择。

调整日期、滚动窗口、滞后、分组或基准时，优先由前端参数控件触发确定性重跑，不必每次调用模型。Agent
负责解释新旧结果为什么不同。

## 4. 研究协议

### 4.1 协议登记表

每一种正式研究能力都由登记表提供，不让模型自由拼接任意统计流程。建议的核心定义如下：

Research Agent 的所有数据问题统一先生成 `ResearchPlanSpec`。Universe、时间序列、Panel 和事件只是不同输入，
不能决定是否允许模型写 SQL；模型在任何分支都不生成 SQL 或执行代码。没有登记数据能力或协议时，系统明确
返回能力缺口，并可交给 Research Curator 形成候选需求。

```ts
interface ResearchProtocolDefinition {
  id: string
  version: number
  questionTypes: string[]
  requiredInputs: ResearchInputDefinition[]
  parameterSchema: unknown
  assumptions: ResearchAssumption[]
  executor: string
  resultSchema: unknown
  diagnostics: ResearchDiagnosticDefinition[]
  formulae: ResearchFormula[]
  pythonExamples: ResearchCodeExample[]
  helpSlugs: string[]
}
```

登记表是方法、公式、代码示例、诊断和文档链接的共同来源。每次运行冻结 `protocolId`、`protocolVersion`、
参数和数据水位；协议升级不能静默改变旧研究。

模型可以：

- 判断问题类型并填写结构化计划；
- 解释变量口径，提示需要用户选择的歧义；
- 根据结构化结果生成通俗说明；
- 建议下一步研究或转因子。

模型不可以：

- 临时发明一个未登记的方法并把结果当成正式证据；
- 自行修改显著性阈值、删异常值或挑选最有利区间；
- 在结论文本里给出结果对象中不存在的数字；
- 绕过数据可得时间、实验计数、holdout 或权限边界。

### 4.2 统一结果契约

每次研究至少返回：

- 问题与可反驳条件；
- 数据范围、样本量、缺失率、频率、币种、基准、时点对齐和数据截止日；
- 点估计、区间估计、效应量和适用的检验结果；
- 方法假设及实际诊断；
- 全样本、分时期、分状态或滚动稳定性；
- 多次尝试、替代口径和稳健性检查；
- 结论等级：支持、弱支持、不支持、无法判断；
- 已知限制和下一步，而不是只有一段流畅总结。

结论文字必须由结构化结果生成并校验数字引用。`p < 0.05` 不能单独等价为“有投资价值”，不显著也不能被
改写成“接近显著”。

### 4.3 研究语义目录的持续维护

研究语义层不是一次性建设。数据域、供应商字段和本地表持续增长时，必须同步评估并登记 Research 能力；否则
数据虽然已经落库，非技术用户和 Research Agent 仍然无法可靠使用。

这里通常增加的不是新的 Spec 类型，而是现有语法可以引用的目录项和确定性实现：

- `EntityTypeDefinition`：对象类型、稳定身份、市场和生命周期；
- `MeasureDefinition`：指标 ID、含义、单位、频率、空值与变换规则；
- `SeriesDefinition`：时间序列 ID、发布日期、available date、vintage 和 revision；
- `EventDefinition`：事件时间、来源、可得时间和去重规则；
- `DataLoader`：通过 Prisma 或参数化静态 SQL 读取并执行 PIT/对齐语义；
- `ProtocolCompatibility`：哪些指标可以进入哪些研究协议和角色；
- 中英文解释、数据来源、覆盖范围和测试 fixture。

只有现有的 entity set、series、event、alignment、protocol 和 output 等组合原语无法表达一个新的研究语义时，
才允许新增 Spec 类型。Spec 不得暴露任意表名、字段名、JOIN、SQL 表达式或执行代码。

因此，新增或实质改变一个研究数据域的完成定义必须包括：

1. 判断它应公开为对象、指标、序列、事件，还是只作为内部实现数据；
2. 登记稳定语义 ID、单位、频率、PIT/vintage/revision 和覆盖信息；
3. 实现并测试 loader、对齐规则、权限和数据质量失败方式；
4. 声明适用协议、图表和不支持的用途；
5. 增加中英文说明与至少一个真实研究 fixture；
6. 更新 Research 能力索引，使 Agent 和 Curator 能发现该能力。

表的机械拆分、索引或存储优化若不改变研究语义，不需要创建新目录项；只需保证已有语义 ID 和运行结果保持
兼容。反之，即使没有新增数据库表，只要单位、可得时间或计算定义发生变化，也必须升级语义版本并说明旧研究
如何重放。

### 4.4 Research Skill、Concept Registry 与对象解析

领域研究知识不继续堆进全局 Agent prompt，也不把数据库实体代码复制进领域说明。系统采用三层边界：

- `ResearchSkillRegistry` 按需加载某个研究方向的候选变量、常见假设方向、研究步骤和禁止替代规则；
- `ResearchConceptRegistry` 用版本化概念 ID 登记中英文名称、别名、词法检索词、优先对象类型和不可替代概念；
- 本地 Research Catalog 用 Prisma 对真实对象、宏观序列、利率曲线和汇率做词法召回，返回精确 `source`、
  `compatibleMeasure`、单位和版本。

Skill 只能引用 `commodity.gold.price`、`rates.us_treasury.real` 等概念 ID，不能保存 `AU.SHF`、
`518880.SH` 等数据库实体。概念检索返回多个语义不同的代理变量时由用户确认；返回空时只表示该精确概念没有
登记的本地序列，不能扩大解释为协议或全部相关数据缺失。

`searchResearchCatalog` 接受结构化 `ConceptQuery`：`conceptIds` 用于领域概念，`text` 仅用于用户明确给出的
对象名称或稳定代码，`filters` 表达对象类型、数据源类型和利率期限。首版使用别名与字段词法召回，不引入向量
索引；未来若增加向量召回，它也只能补充候选，最终仍须通过本地目录验证精确身份和研究契约。

## 5. 第一批研究协议

第一版不追求覆盖全部统计学，而是用三类高频问题建立完整产品闭环。

| 协议 | 典型问题 | 主要方法 | 主要输出 | 必要诊断 |
|---|---|---|---|---|
| 描述与分布比较 | 两组股票估值、收益或风险有何差异 | 分位数、效应量、箱线图、适合样本的差异检验 | 分布、差异区间、异常值敏感性 | 样本量、偏度、缺失、分组不平衡 |
| 时间序列变量关系 | 利率与风格收益、黄金与股票相关性 | Pearson/Spearman、单/多变量回归、HAC、滚动统计、状态分组 | 相关/回归系数、区间、滚动稳定性、散点回归图 | 自相关、滞后选择、结构变化、共同趋势、前视风险 |
| 事件研究 | 公告或政策事件前后市场如何变化 | 事件窗、基准调整异常收益、累计异常收益、置信区间 | 事件路径、CAR、横截面分布、分组结果 | 事件重叠、基准选择、样本选择、公告可得时间 |

首个垂直切片选择“时间序列变量关系”。它同时覆盖数据对齐、频率、滞后、回归、滚动稳定性和互动图表，
最能验证工作台是否真的比一次性 Agent 分析可靠。

后续由真实问题拉动扩展：Panel 分析、横截面比较、风险归因、组合比较、季节性、状态切换和稳健性检验。
ROADMAP 4.1 负责审计与补充方法正确性，本设计负责把已审计方法变成用户可调用的协议。

## 6. 互动图表与参数探索

互动图表不是装饰，而是让非技术用户看见关系是否稳定、是否被少量样本驱动。第一批需要：

- 散点图、回归线和置信区间，可查看样本点对应日期；
- 滚动相关、滚动系数和滚动区间，可调整窗口；
- 时间序列叠加与标准化比较，可切换原值、变化率和收益率；
- 状态分组、箱线图、直方图和分位数；
- 事件窗路径和置信带；
- 相关性热力图、回撤图和贡献图作为后续扩展。

所有控件都应显示当前参数，并进入运行 spec。参数变化生成新运行或明确的临时预览，不能让图已经变化而
结论、公式或保存记录仍引用旧结果。

## 7. 公式、Python 示意和解释文档

每个方法结果提供一个“这是怎么计算的”区域，至少包含四层：

1. 通俗解释：这个量回答什么问题，正负、大小和区间怎样理解；
2. 公式：用 KaTeX 展示，并逐一解释变量、下标、样本和权重；
3. Python 示意：用 `pandas` / `scipy` / `statsmodels` 展示等价的教学代码；
4. 延伸阅读：项目内中英文概念文章和少量权威外部来源。

例如时间序列关系可以展示 Pearson 相关系数、线性回归和 Newey–West/HAC 标准误的公式与含义。Python
示意代码来自经过测试的模板，并标注它是教学复现还是生产执行实现；不能让模型根据结果随手生成看似合理、
实际口径不同的代码。

帮助链接由协议登记表提供，可以按结果上下文进一步推荐：相关不等于因果、置信区间、效应量、自相关、共同
趋势、结构突变、PIT 与前视偏差等。内部文章是稳定主链接，外部资料作为参考文献，不依赖即时搜索结果成为
唯一解释来源。

## 8. Agent 与执行架构

### 8.1 通用研究 Agent

新增独立 `research` profile/surface，复用统一 Agent 的对话、turn trace、工具审批和持久化能力。它与 Screen
Agent 可以共享查数和图表工具，但默认目标不同：Screen 返回符合条件的证券集合，Research 返回一个研究计划
和版本化研究运行。

宽泛领域问题先从轻量 Skill 索引判断是否存在适用方向，再通过 `loadResearchSkill` 按需加载详细策略；首个
fixture 是黄金价格驱动研究。Skill 给出 Concept ID，`searchResearchCatalog` 负责解析真实对象，Agent 不根据
Skill 或模型记忆猜数据库代码。

建议的工具边界：

- `resolveResearchInputs`：将自然语言变量解析为稳定数据字段和派生口径；
- `planResearch`：输出受 schema 约束的研究计划；
- `runResearchProtocol`：只能运行登记协议和合法参数；
- `compareResearchRuns`：解释数据、参数、协议或环境差异；
- `proposeFactorDraft`：只生成转因子建议和草稿预览；
- 现有只读 SQL 与隔离计算基础设施只可作为登记 loader/protocol 的底层实现，不向 Research Agent 暴露
  `sqlQuery`、`analyzeData`、`renderChart` 或 `renderComputedChart`。

### 8.2 数据与持久化

对话不是研究结果本身。建议逐步形成：

- `ResearchStudy`：用户问题、假设、状态和关联对话；
- `ResearchRun`：协议版本、运行 spec、数据摘要、结果、诊断和环境指纹；
- `ResearchAttempt`：不覆盖成功结果的失败计划、错误、父运行和 Agent trace 来源；
- `ResearchPromotion`：向 Factor / Strategy 提升的来源、目标和审批动作；
- 图表和解释文本作为运行产物引用，而不是唯一事实来源。

第一版可在现有 AgentConversation 持久化之上保存最小 `ResearchRun`，不必先建设自由 notebook 单元格。研究
记录、data revision 和环境指纹属于工作台的可信基础能力，而不是单独的产品主线。

### 8.3 Screen 退场与 Universe 能力

现有 Screen 不再作为独立产品入口，也不作为新研究工作台的兼容子模式。它的三项职责一次性拆分：

- Screen Agent 对话迁入 Research Agent；
- 股票筛选改造成研究协议可以引用的 `UniverseSpec V1`；
- 股票 K 线升级为独立的跨资产对象详情页。

新架构不先复用或扩展 `ScreenSpec`。M0 直接冻结最终的 `UniverseSpec V1`，至少明确：

- Universe 类型、资产类型、市场和稳定对象身份；
- `asOfDate`、历史可投资状态、上市/退市、停牌和成分有效期；
- 字段标识、字段版本、比较操作、缺失值规则和单位；
- PIT 可得时间、数据 revision、排序、上限和结果字段；
- 手工对象、指数成分、保存的 Universe 和条件筛选等来源；
- 用于研究运行时冻结的 Universe 成员快照及生成依据。

`ScreenSpec` 只作为上线前迁移程序的输入，不能成为新 API、数据库字段或运行时依赖。切换前先对全部旧记录做
迁移预检：可无损表达的 SavedScreen 转为保存的 Universe；不能无损表达的记录必须在切换前修复、明确放弃或
导出。正式切换以一次数据库迁移完成，并在同一发布中删除 `/screen` 页面和路由、Screen profile、Screen 专属
API/类型、SavedScreen 与旧 ScreenConversation，不保留长期双写、兼容重定向或两套入口。

应用层迁移由幂等的 `migrate:screen-to-research` 命令完成，并在 bootstrap 的 Prisma schema 升级前后各运行一次：
升级前保证未来删除旧表时数据已经转出，升级后兼容没有旧记录的空数据库。若旧数据存在但目标 Agent 表尚未
创建，脚本会阻断部署，要求先升级 Agent conversation foundation，避免跨版本直升时静默丢数据。脚本用旧记录 ID
作为稳定的 Research 对话 ID，静态映射全部 Screen 字段，将 query card 转成受 schema 校验的 Universe part，
并在单一事务内验证 owner、消息前缀、turn 归属和迁移结果。旧表不存在时命令必须成功 no-op；`--dry-run` 执行
完整写入与验收后回滚。迁移阶段只为仍在线的旧 Screen 保留源记录，最终切换的 schema migration 负责删除它们。

当前 `runScreen` 也不是把 `ScreenSpec` 拼成 SQL。它先通过 Prisma 分别读取最新交易日的全量 `DailyBasic`、
`Daily` 和 `StockBasic`，在应用内合并成行，再由纯函数执行过滤、排序和截断。这个实现只适合小型最新截面筛选，
不能作为 Universe 引擎继续演进。

新的 Universe 执行器应先校验 `UniverseSpec V1`，再编译为类型化、参数化的查询计划；简单条件尽量下推数据库，
历史可投资状态和 PIT 连接由确定性领域代码完成。模型只能生成和解释 spec，不能生成字符串 SQL 或改变查询
语义。

### 8.4 跨资产对象详情

`/stock/:code` 政策上退出，改为统一对象详情路由。对象引用必须包含稳定 ID 和类型，不能只靠代码猜测资产。
Research Agent、研究表格、图例、因子报告和回测结果都通过结构化引用跳转到该页面。

详情页按对象类型选择视图：股票与 ETF 可显示复权 K 线和成交量；指数显示价格、收益、估值和成分；期货显示
实际/连续合约、结算、持仓量与换月；利率、汇率、宏观和商品库存显示带单位、频率、发布日期和 revision 的
时间序列。K 线是适用于部分资产的一种视图，不是详情页的共同数据契约。

同时把现有只搜索 A 股/ETF 的 `searchInstruments` 替换为跨资产、跨序列的统一对象搜索。它供全局搜索、Research
Agent 和实体链接共同使用；搜索结果必须来自本地对象目录，不能由模型根据名称猜代码。

## 9. 研究整理 Agent（Research Curator）

### 9.1 为什么不能只做一次 LLM 总结

纯 LLM 可以归纳聊天，却无法可靠回答以下问题：

- 用户临时搜索的数据是否已经存在于本地表；
- Tushare 是否真的提供该接口、字段、历史范围和当前权限；
- 相同能力是否已经在代码、ROADMAP、帮助文档或待办中；
- 一段临时代码是否足够通用，值得升级成正式研究协议；
- 数据落库是否满足 PIT、许可、增量同步、质量审计和字段语义要求。

因此需要一个单独的后台 Agent，但闭环必须是：**确定性提取 → LLM 归纳 → 工具核验 → 人工分流 → 正常开发/
数据接入流程**。模型负责发现模式和撰写候选，不拥有自动改 schema、抓取全量数据、修改 ROADMAP 或发布功能的
权限。

### 9.2 输入与分类

增量读取当前用户自上次游标后的对话和 turn trace，并提取：

- 重复出现的问题类型、手写 SQL/计算和图表组合；
- 查不到的字段、工具失败、用户纠正和被拒绝的结论；
- 临时网络搜索或外部数据来源；
- Tushare 接口名、字段名、资产和频率线索；
- 多次出现的概念解释、文档缺口和转因子建议。

候选发现分为：

1. 值得沉淀为研究协议；
2. 供应商已有但本地缺失的数据；
3. 本地已有但 Agent 不知道或工具不可达的数据；
4. 值得增加的帮助/概念文章；
5. Agent、工具或交互缺陷；
6. 一次性需求、重复项或证据不足，不采取行动。

### 9.3 核验工具

Curator 需要只读工具，而不是只看聊天文本：

- 搜索本地 schema、字段目录、SQL tool docs 和同步任务；
- 查询一个版本化 Tushare 能力目录，包括接口、字段、积分/权限、历史深度和最近核验时间；
- 搜索研究协议登记表、设计文档、帮助中心和 ROADMAP；
- 对候选做重复检测，列出支持与反对证据；
- 必要时生成一个待人工执行的数据 smoke check，但不自动扩大供应商调用或落库范围。

每条发现卡包含类别、原始证据、重复次数、核验结果、置信度、预期价值、预计改动面和建议下一步。用户可以
接受、拒绝、稍后处理或标记重复；反馈作为后续评估数据，不直接在线训练模型。

### 9.4 触发策略

先实现**手动触发**，便于检查噪声、隐私范围和分类质量。达到可接受准确率并积累足够对话量后，增加默认
每周增量摘要；每日运行作为可配置选项，只在新对话数量达到阈值时执行，避免每天产生相同建议。

Curator 只读取当前用户有权限的对话。跨用户聚合必须匿名化并由管理员显式启用，不能让一个用户的研究问题、
持仓或未公开因子出现在另一个用户的建议中。

第一版成功指标：建议被接受率、重复建议率、核验错误率，以及最终转成协议、数据接入、文档或缺陷修复的
比例。摘要写得好看不算完成。

## 10. 开发里程碑

### M0：冻结协议与结果契约

- 建立 `ResearchQuestionSpec`、协议登记表、统一结果和结论等级；
- 为三个首批协议准备固定 fixture、错误样本和中英文术语；
- 冻结公式、Python 示例与帮助链接的元数据格式；
- 写清 Agent 可决策项、必须确认项和禁止自动化项。
- 直接冻结 `UniverseSpec V1`、统一对象身份和跨资产详情契约，不扩展旧 `ScreenSpec`。

**验收**：同一 fixture 在协议版本和参数不变时得到一致结构化结果；错误口径能被拒绝，而不是被模型解释过去。

### M1：时间序列变量关系垂直切片

- 新增 Research Agent 入口与研究计划卡；
- 完成变量解析、对齐、变换、滞后、相关、回归/HAC 和滚动稳定性协议；
- 完成互动散点、滚动图、参数控件和结构化结论；
- 展示公式、Python 示意、概念文档和数据口径；
- 覆盖中文/英文和端到端测试。
- 用 Research 入口取代 Screen，完成旧筛选/会话的一次性迁移和 Screen 专属链路删除；
- 上线统一对象搜索、结构化实体链接和跨资产详情的首批视图。

**验收**：一个不懂代码的用户可以从自然语言问题完成研究，能回答“算的是什么、为什么这样算、结果是否
稳定、有哪些限制”，并可用相同参数重跑。

### M2：扩展研究问题与图表

- 上线描述/分布比较和事件研究；
- 增加箱线图、置信带、事件路径、热力图等图表；
- 建立方法选择、异常值、缺失和多次尝试的统一记录；
- 用真实用户问题补充协议 fixture，而不是按统计学目录堆功能。

**验收**：三类问题使用同一产品流程，但各自保留正确的假设、诊断和结果结构。

M0–M2 已封板：三个协议当前执行并展示的核心估计、推断方法、稳健性与效应量公式均已进入版本化目录，结果页
按方法分组展示公式和双语变量解释，并继续提供经过测试的 Python 示例与概念文档。后续扩充公式必须随实际协议
实现和测试一起进入长期语义目录，不能只增加脱离计算结果的教材条目。

### M3：研究提升为因子

**状态：暂缓。** 先积累通用研究协议、正式记录和真实研究样本，不让转因子形态反向限制研究工作台。重新启动
时仍须遵守下列就绪规则和因子研究纪律。

- 实现可解释的转因子就绪规则和 Agent 建议卡；
- 点击后创建私有因子草稿，保留研究来源和未解决项；
- 接入现有因子代码校验、正式报告、holdout 与发布流程；
- 测试同期关系不会被误当作未来收益预测。

**验收**：通用研究与因子研究顺畅衔接，但不能通过建议卡绕过任一研究纪律。

### M4：可复现研究记录

- ✅ 保存、重开、父子比较与确定性重跑 ResearchRun；
- ✅ 增加 data revision、应用 revision、协议实现与运行环境指纹，以及确定性差异说明；
- ✅ 记录字段级替代口径和结构化结论是否变化；
- ✅ 单独记录失败尝试；全失败 Study 可被后续成功修正复用；
- ⏸ 研究证据关联 Factor、Strategy 和正式报告随 M3 一并暂缓，不作为当前研究工作台的完成条件。

**验收**：结果变化时可以区分协议、参数、代码、数据和环境原因。

### M5：研究整理 Agent

- ✅ 建立 owner-scoped 增量游标、确定性证据提取、严格 JSON 分类、目录核验和发现卡；
- ✅ 上线手动后台运行、跨运行指纹去重和接受/拒绝/延后/重复人工分流；
- ✅ 接入 Research 能力、只读本地数据、版本化 Tushare 能力与持久化探测结果，以及代码、帮助、ROADMAP 和
  设计文档的只读重复检索；
- ✅ 独立记录核验正确性反馈，并持续显示接受率、重复率和核验错误率；未达到最少 20 项已审候选和 20 项人工
  核验时只报告样本不足；
- ⏸ 每周调度须在真实人工标注达到样本规模并完成质量复盘后另行评估；每日调度保持关闭。

**验收**：Curator 能用证据指出“应沉淀什么、已有但没用到什么、供应商可能补什么”，且不会自行改库、
跨用户泄漏或反复产生相同建议。

### 长期维护：数据能力登记

M0–M5 完成后，本设计继续作为数据工作的长期约束。每次新增或实质改变研究数据域，都按 4.3 完成语义登记、
加载器、协议兼容性、双语说明和 fixture。Research Curator 定期检查“本地已有数据但语义目录不可达”和
“聊天反复需要但尚未登记”的缺口，人工确认后进入正常数据开发流程。

## 11. 当前不做

- 把聊天包装成自由 notebook 或兼容 `.ipynb`；
- 让 LLM 任意生成 Python 后直接作为正式统计结果；
- 自动批量挖因子、自动转因子、自动揭示 holdout 或自动发布策略；
- 因为图表可交互，就隐藏样本、假设、不确定性和数据口径；
- Curator 自动修改产品、落全量供应商数据或代表用户决定优先级；
- 一次覆盖全部统计学方法和所有图表类型。
- 为 `ScreenSpec`、Screen Agent 或 `/stock/:code` 建设长期兼容层。
