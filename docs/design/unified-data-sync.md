# 按目标日期统一数据同步

日期：2026-10-23

产品方向已由用户确认：daily、weekly、repair、import、sync、canonicalize 合并为一个 sync。用户允许推翻现有设计，不要求旧命令、旧执行协议和旧目录兼容。本文给出产品契约、实施边界及验收标准；具体代码、schema、迁移和提交信息由开发者按 review-gated-development 提交 Gate 1 后实施。

开发交接见 [GPT-6 sol 开发 prompt](unified-data-sync.prompt.md)。完整实现和开发验证完成后，由用户将交付结果带回设计会话，进行独立验收。

## 产品目标

用户指定目标日期，系统尝试获取各类可用数据，保存合法记录，更新当前能够成立的计算，并报告实际覆盖和未完成项。再次执行同一命令，继续处理缺口、晚到数据、来源修订和未完成计算。

目标日期为 20260915 时，行情截至 20260915、资金流截至 20260914、财报仍为最新已公开季度，是合法的数据状态。系统不能把各数据集最后日期必须一致作为全局发布条件，也不能将目标日期显示为“所有数据已完整到这一天”。

首次初始化、历史补齐、日常新增、失败恢复和已有记录修订属于同一流程。定时调度只决定何时再次调用 sync；系统不再保留 daily / weekly 两套业务流程。

“拿到多少算多少”适用于合法数据的获取和保存。数据质量、计算所需的同日对齐、实际可得时间和结果可复现性仍有明确约束。

## 命令与范围

本轮唯一面向用户的市场数据写入口为：

```bash
pnpm data sync
pnpm data sync --to 20260915
pnpm data sync --help
```

- 根级命令和 API package 的对应入口执行同一实现。直接执行编译后的 Node 入口用于部署，不能另有业务分支。
- 不传日期时，目标为本次运行开始时的上海自然日；各数据集依据自己的交易日历、时区、周期与发布时间判断该日期以内哪些记录可以请求。未完成交易日不因此产生虚构的收盘数据。
- `--to` 是数据观察日期或所属期间的上限，不表示所有来源已齐备，也不表示重现该日实时可得的完整数据库。来源公布时间、历史可得时间与抓取时间分别保留。
- 对已含较新数据的库执行较早 `--to`，只限制本轮获取范围，不截断较新记录、不回退已有覆盖事实。历史修订若影响目标之后的已有派生结果，仍须标记失效并重算，或明确保持 stale；不能借目标上限忽略真实依赖影响。
- 目标在一次运行中固定。继续未完成分片时保留该分片的固定边界；新一次默认运行可以产生更晚目标，同时保留以前的未完成项。
- 日期须校验真实日历日期，未知参数与多余参数报错。帮助、非法参数在读取业务环境、连接数据库或发请求之前结束。
- 不增加 `--daily`、`--weekly`、`--repair`、`--import`、`--initialize`、`--resume`、`--force` 等模式开关，也不以新名称保留六条旧流程。
- 此次不增加数据集选择或手工刷新模式。数据域范围与历史起点由明确的数据目录配置，单项业务函数仍可供测试及内部组合调用。
- 无参数的 `pnpm data` 只显示帮助；无参数的 `pnpm data sync` 执行同步。

删除原 `maintenance daily/weekly/repair/import/sync/canonicalize`、`import:data`、`sync <task>`、`canonicalize:stock-codes` 的写入口及旧分派。候选清理成为运行资源的自动回收，不再需要用户完成一次正常同步后手工 cleanup。

独立备份、只读审计与外部接口探针保留其工具职责；它们不是完成同步所需的额外步骤。本轮不新增数据管理页面、HTTP 写入口或其他顶层操作命令。

## 一套执行流程

```text
固定目标，读取实际覆盖和未完成项
  → 为各数据集生成有限的请求分片
  → 获取数据，校验记录与响应完整性
  → 提交合法变化、覆盖状态及受影响结果的失效标记
  → 对输入已满足要求的结果计算并审计
  → 发布计算结果及其输入版本，报告仍未完成的工作
```

不同数据集可以拥有不同请求粒度、修订周期和限流，但使用同一运行流程。一处来源失败后，继续处理不依赖它的工作。不可恢复的数据库或发布技术故障可以终止本次运行；已经正确提交的独立批次不因此被伪造回滚。

运行按有限分片执行并保存进度。长历史允许分批推进，不要求多年数据和全部派生一次成功才使任何数据可见。必须防止某个持续失败的数据集无限重试，或历史回填长期饿死新数据同步。

## 数据目录与完成判定

每个数据集只声明实际需要的规则：

| 规则 | 必须回答的问题 |
| --- | --- |
| 对象与历史边界 | 同步哪些证券或序列，从何时开始；上市、生效、退市和来源能力如何限制范围 |
| 日期与可得性 | 使用哪个日历、时区和观察周期；如何表达公告、availableDate、vintage 与抓取时间 |
| 请求与完整性 | 按日期、代码、报告期还是分页获取；怎样确认一个响应完整 |
| 更新方式 | 新增、修订、来源删除怎样识别；完整替换与部分合并各在什么条件下成立 |
| 重查策略 | 哪些未完成项必须再次请求；近期修订窗口、较早历史巡检如何推进 |
| 数据检查 | 日期、身份、单位、值域、唯一性及跨字段关系有什么约束 |

Gate 1 须列出各数据集的实际历史起点、默认范围与重查规则，集中保存确定的配置，不能继续沿用分散脚本中互相矛盾的默认日期。来源更早资料若只用于计算预热，应与目标输出范围区别。

覆盖不能仅用最大日期、行数大于零或“请求执行成功”表示。需要同时知道已取得的范围、未完成的分片或业务键，以及最近一次请求和核验结果。状态应按数据集实际分区粒度存储，避免为每个单元格建设通用任务系统。

合法空集也有语义：休市、证券尚未上市、事件型数据当日没有事件，可在有依据时判定不适用或完整空集；来源超时、异常空响应、分页未完成、部分返回不能据此标记完成。无法证明的空响应保留待核验状态，不能假定供应商尚未发布或已经全部返回。

每次 sync 都考虑新日期、已有未完成项和到期重查项。已取得较晚日期不能跳过较早缺口。历史修订检查按配置和游标推进，无需每次全历史重新下载；未核验的历史不能声称已核验。

## 部分返回与安全写入

必须逐一检查原同步函数的空响应、分页、批量替换、跳过与 checkpoint 逻辑。仅放宽最终审计不足以实现本设计。

1. 响应内合法记录可以按稳定业务键合并。尚未确认完整时，不得用删除整个日期或分区再插入本次记录的方式覆盖好数据。同一业务键还须区分“未返回或未知字段”与“来源明确修订为 null”：前者不能抹除已知值，后者按该来源契约更新；含义不明时保留异常待核验。
2. 已有好记录遇到未经证明的空响应、请求失败或非法记录，保留好记录和异常信息，安排后续核验。
3. 只有确认完整且有权威范围语义的响应，才允许原子替换其精确范围。明确完整且权威的空集可以表示正式删除并清除对应精确分区，须记录删除依据并使依赖失效。正式来源删除、修订也必须能够传播，不能机械地把所有操作改成只增不减。
4. 对有原子单位的数据按单位校验，例如完整成分权重快照或一个不可分的财报版本；不将半份快照冒充有效完整对象。不能接受的响应可以留诊断，其他独立数据仍可提交。
5. 数据变化、对应覆盖/checkpoint 与派生失效标记须原子一致。先标完成后写数据，或先写数据却没有可靠的待计算记录，都不成立。
6. 证券代码归一是具有历史有效日期的身份规则和必要的已有记录整理，不是粗暴改字符串；归一后的业务键不得产生重复、孤儿或错误历史归属。

本条是对仓库原“按日 deleteMany + createMany”约定的有界调整：它继续适用于已经证明完整的权威日期分区，不能用于不完整响应。实施时同步修正文档中的适用条件。

## 审计分为三个问题

| 问题 | 例子 | 结果如何使用 |
| --- | --- | --- |
| 数据是否合法 | 错误代码、非法日期、单位错误、重复冲突、错误可得时间 | 拒绝或隔离相关记录或原子对象 |
| 数据覆盖到哪里 | 目标 09/15，资金流只到 09/14；某日只取得部分证券 | 报告缺口、新鲜度和请求异常，后续重试 |
| 某项计算是否成立 | 截面覆盖不足、缺少复权、风险拟合缺少样本 | 阻止该项计算成为正式有效结果，其他独立工作继续 |

不能把所有现有 error 改为 warn，也不能删除所有 coverage 检查。需要给每项 finding 明确作用对象和影响范围，停止用“存在任意审计 error”否决整库合法更新。

市场风险模型所需的 252 个完整观测等要求属于模型就绪规则，不应成为股票价格保存条件。完整截面、收益、成交约束所需的要求仍由具体消费者执行。

同步成功表示本次尝试及提交按约定完成，不能暗示覆盖完整。建议命令结果区分：

- `complete`：本次计划内工作完成，结果同时列出实际覆盖。
- `partial`：合法进展已经保存，仍有等待来源、缺口或待计算项。
- `error`：存在真实请求/校验/计算异常或技术失败；独立成功提交仍列出。

退出码约定为：0 表示 complete 或仅存在可解释的等待/有限批次剩余的 partial；1 表示真实异常，包括失败但已有部分进展；2 表示参数错误；75 表示另一写者占用。摘要必须列出状态、目标、实际覆盖、缺项和错误。不能把无法解释的空响应或永久缺口都归为正常延迟来长期返回绿色。

## 计算的日期与版本

各计算声明真实输入、时间对齐方式、历史窗口、最低覆盖及计算版本。以普通业务函数和显式配置实现即可，不建设通用 DAG 平台。

- 精确同日输入，例如当日收益、资金流和撮合约束，缺失时不能默认沿用昨天或填零。
- latest-known / as-of 输入，例如截至决策日可得的财报或允许沿用的利率，保留实际观察日、可得时间及适用的新鲜度规则。
- 不同证券或序列做截面、收益比较或联合建模时，明确共同样本与对齐规则。来源日期不同不自动证明错误，也不自动证明可以混算。
- 市场上涨比例、涨停数量和气象热度等不得将部分股票样本伪装成全市场。保留覆盖信息；输入不足时结果暂缺、明确 partial，或显示带自身日期的上一有效值。
- 具有正式用途的消费者须检查输入资格。已有股票截面因缺估值而缩小股票池等行为需要检查和披露，不能让放宽入库条件悄悄改变正式因子/策略样本准入。

数据新增、晚到、修订和正式删除产生真实变化范围，再按依赖与滚动窗口传播。无关元数据变化不触发全历史计算。计算版本变化即使没有原始数据变化也须使对应结果失效；审计版本变化须重新判断资格。

结果就绪信息至少包括输出范围、实际输入日期/范围、输入修订标识、计算版本与缺项。旧结果保留时必须明确 stale 或其原日期，不能作为已经更新完成的值返回。

原始变化与派生失效标记在同一短事务中提交；计算在固定输入版本或受保护的读作用域内进行。结果与其就绪状态一起提交，并拒绝把过期计算发布到较新的输入版本上。不得在跨数据集网络请求期间持有全库写事务。

缓存也受输入变化影响。只以最大日期为 key 的缓存必须处理同日补齐和历史修订，否则计算更新而用户仍看到旧值。

## 数据更新与已有研究结果

区分观察日期、来源公开/可得时间与实际抓取时间。09/15 的记录若到 09/16 才公开，不能用于模拟 09/15 当时的决策。仅抓取晚了、但当时确实已公开的记录，可以改变今天重跑的历史研究输入；这种变化须可解释。

只知道最新修订值、缺少历史 vintage 的数据，不得被标成已证明严格 PIT。不能为了让新流水线通过而补造历史可得时间。

本次同步不会自动改写已有回测报告、因子报告、封存 ResearchExecution、已执行信号、账户和成交。新的分析可以使用新数据，持久化的结果继续按其现有不可变契约保存。记录版本号不等于保存了可回放输入；不得凭新增 revision 字段宣称所有历史报告已经完全可复现。

当前派生看板允许在数据变化后更新，须注明日期和缺项。因子气象按已完成周期及其输入资格刷新，不必追到统一目标日期。信号/账户与因子气象只消费满足自身要求的数据，其失败独立重试，不否决无关市场数据。

本轮不要求自动重跑所有用户策略或重写任意用户因子算法。对新的部分可用状态，消费者要么按已有明确规则处理，要么返回具体不足；需要改变正式统计准入或金融计算口径时，必须在 Gate 1 明示。

## 存储与职责

产品契约不绑定现有 candidate、全局日水位、旧 MaintenanceRun kind 或目录结构。可以复用经过验证的锁、隔离与事务能力，但不能通过保留旧六分支实现来假装完成合并。

| 责任 | 归属 |
| --- | --- |
| 获取、解析、证券身份、数据集质量 | Market 对应数据域 |
| 覆盖与重查计划、运行恢复、进度和统一入口 | 一处同步协调模块 |
| 市场派生及气象的计算规则 | 各自业务域 |
| 因子/策略/信号的输入资格与运行 | 各自业务域 |
| 数据库连接、跨进程互斥、读一致性 | infra |

同步协调继续留在 API workspace，避免额外部署服务。使用具名输入与结果类型，业务函数不解析 `process.argv` 或 CLI `string[]`，不替调用者关闭数据库。Market 不反向依赖 Strategy、Factor、Research、Signals 或协调模块；跨域组合在协调层完成。

Gate 1 需要给出最小持久化模型，覆盖运行目标与结果、数据集分区覆盖/未完成项、计算失效与版本。不要为每条原始记录建立 Job，不复制一套通用调度器。原始数据 schema 只有在业务语义确有需要时修改。

全局 revision 可以继续表示可见数据发生变化，不能再被解释为所有表齐备到同一天。短暂发布互斥、用户执行期间一致读取、并发写入串行化仍须保证。某来源待更新、部分缺数或空库不应封锁整个产品；对应页面显示空态或局部不可用。数据库技术故障仍需真实报告。

无历史兼容要求意味着可以删除旧 CLI、协议和控制流程；不意味着可以删除用户数据、真实行情或擅自重置数据库。旧运行/候选的退役和资源处理在实施计划中明确，允许停止恢复旧协议，不建立永久兼容层；不得误清理活跃写者或不属于本次运行的文件。

## 实施范围

需要一次完整覆盖以下关联面，不以“先统一命令，业务以后再改”交付：

1. 统一 CLI、参数、运行与摘要；删除六条旧公开写流程。
2. 24 项现有同步能力及原维护中的必要能力；来源完整性、增量/修订写入、覆盖与重查。
3. 原始检查、覆盖报告、计算资格的分离，依赖失效与局部计算。
4. 运行恢复、并发、数据和状态事务、用户读取一致性、自动资源回收。
5. Market/Factor 气象、Research 数据会话/缓存、Strategy/Factor/Signals 输入资格等现有消费者的必要适配。
6. 当前状态接口、维护门禁、现有页面空态/日期/缺项与双语文案；不另建数据管理产品。
7. root/API package 命令、bootstrap、激活脚本、systemd 与当前文档。一个定时服务调用统一 sync；具体触发频率在 Gate 1 说明，不能将来源更新时间重新包装成 daily/weekly 流程。
8. Prisma schema/生成迁移、共享 HTTP 契约、SQL_TABLE_DOCS、测试及部署清单中实际受影响的部分。

## 开发与审阅流程

开发者使用 [review-gated-development](../../../../.codex/skills/review-gated-development/SKILL.md)。保持一个完整、可审阅的实现范围，不发明任意阶段或仅交付入口改名。

拟议精确提交信息如下；Gate 1 核对后由用户批准，若范围改变导致信息改变，应在编码前重新说明：

```text
feat(market)!: unify data synchronization by target date

Replace separate maintenance workflows with one date-targeted sync.
Track dataset coverage independently and compute from eligible inputs.

BREAKING CHANGE: Replace the maintenance, import:data, sync task, and
canonicalize:stock-codes entry points with data sync.
```

### Gate 1

先只读核对现状，提交完整实施计划：具体入口和目录、数据集策略表、持久化模型、部分写入与删除语义、发布/读取一致性、消费者适配、旧控制状态退役方式、部署联动、静态检查与行为验证，然后等用户批准。产品方向无需重新选择；具体实现和迁移尚需此门禁。

### 静态检查与 Gate 2

实现全部产品与测试代码后，仅执行静态检查，再提交未 commit 的 diff 供人工审阅。先检查组合命令：

- API `tsc --noEmit`、适用 workspace 类型检查、ESLint、Prettier、`git diff --check`。
- 后端边界使用 `node scripts/checks/check-backend-boundaries.mjs`；`pnpm check:backend-boundaries` 带自测，留到审阅后。
- 若改 Shell 或独立 MJS，可用 `bash -n`、`node --check`。
- 根 typecheck 或 SDK 检查先核对实际实现，只有不含构建、应用执行或数据库操作的静态路径才可提前执行。

Gate 2 前不运行单元/集成/E2E、构建、应用或真实 CLI、外部接口探针、真实同步及数据库写操作。必要的 Prisma Client 生成须确认仅由 schema 生成文件、不操作数据库。

Prisma migration 必须由 Prisma 生成。默认在首轮 Gate 2 批准后，用隔离临时开发/影子数据库生成；新增 SQL 属于产品变更，需再次提交 Gate 2 后才能继续剩余验证。若希望将生成 SQL 一并纳入首次审阅，必须在 Gate 1 明确取得“仅隔离库生成迁移”的窄例外授权，不能把 migrate dev --create-only 称为静态检查。

### 验证与提交

人工 Gate 2 批准后运行下表验证和受影响构建。批准同时授权在全部必需验证通过后，按预告信息提交，满足仓库 commit 确认约定；不 push。

产品代码修正后回到 Gate 2；已批准范围内的纯测试/fixture/harness 修正可自行修复、静态检查并复验，不额外请求产品审阅。不得降低断言来获得通过。

使用临时 SQLite 和受控 provider/通知替身。真实供应商调用、真实库长区间同步与部署不属于本次开发验证的默认授权；需要时另列具体目的与范围。清理所有测试进程、监听、Worker 和数据库连接。涉及 UI E2E 时检查并在交付中展示实际截图。

## 验收矩阵

| 编号 | 场景 | 必须证明的行为 |
| --- | --- | --- |
| A01 | CLI 与旧入口清理 | 唯一写流程是 data sync；帮助/非法参数无业务副作用；源码和干净编译入口都能执行；部署无旧调用 |
| A02 | 空库初始化与长历史 | 一个 sync 自然开始全部已声明数据域；有限分片可续跑，无需 import/initialize；批次成功不冒充历史全部完整 |
| A03 | 目标 09/15，某来源只到 09/14 | 合法数据保存并可读，实际日期不改写；只阻止依赖未到输入的计算，不封站 |
| A04 | 目标已推进后晚到旧日期 | 09/16 运行仍获取缺失的 09/15；最大日期和非零行数不能错误跳过 |
| A05 | 同一分区分批返回、空响应与错误值 | 有效记录累计；同键未返回/未知字段不抹除好值；已有数据不被未知空/半批覆盖；合法空集、未知空响应、请求失败明确区分 |
| A06 | 权威修订、删除与原子对象 | 完整权威空集可删除精确分区，明确 null 修订按契约更新并传播影响；半份权重快照不成为有效快照；代码归一不造成重复或历史身份错误 |
| A07 | 局部失败与退出结果 | 独立数据和计算继续；实际错误不伪装正常延迟；摘要/退出码准确，错误项保留重试依据 |
| A08 | 计算资格与不完整截面 | 价格可用不要求资金流齐备；收益/撮合不借昨日值；缺复权、缺估值、样本不足不被静默填零或当作完整截面 |
| A09 | 延迟、PIT 与已有结果 | 区分观察/可得/抓取时间；不能使用决策后公开数据；旧报告、封存研究、信号、账户、成交不被同步改写 |
| A10 | 真实输入变化与版本失效 | 晚到、历史修订、删除仅传播必要影响；较早 --to 不截断较新数据，目标之后受影响结果仍失效；公式变更可在原始数据不变时重算；同日更新使缓存失效 |
| A11 | 崩溃恢复与幂等 | 在数据提交、状态提交、计算、结果发布边界注入失败；恢复不漏项、不重写用户数据、不发布错版本，重复运行不重复记录 |
| A12 | 并发与读取一致性 | 同时运行不会竞争覆盖；一个用户计算不混读发布前后输入；局部 partial 不变成全局不可用 |
| A13 | 自动回收与后续业务 | 活跃资源不误删；独立失败的信号/气象可重试；已执行信号不重复结算或发出真实通知 |
| A14 | 完整能力与契约联动 | 24 项能力及原维护额外能力有逐项映射；相关 API/SDK/双语/SQL 文档/schema/部署规则一致，无整类能力遗漏 |

测试应使用有业务意义的 fixture，覆盖完整日、部分日、不同市场日历、财报版本、完整/不完整快照以及连续/事件型数据。无需每条验收项建立一套镜像测试，但每项必须有可定位证据。

若改变 deployable workspace/package 或跨包构建依赖，同时修改 deploy/component-impact.json 与 scripts/deploy/plan-deployment.test.mjs；仅目录内整理则核对现有映射覆盖，不能机械改清单。
