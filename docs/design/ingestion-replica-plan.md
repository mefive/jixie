# Ingestion 副本采集开发计划

日期：2026-11-04。状态：已确认人工接收／拒绝与发布协调方式，实现已通过人工审阅与隔离验收，待工作库迁移和首次运行。

每个 Run 有一个工作副本。采集、核验和修复在副本进行，人工通过 CLI 接收后，才把这轮的最终变化一次发布到主库。等待审核时，研究、策略和回测继续使用已发布数据。

保留现有自然起点、历史 ETF Top 100 累计名单、批次事务及数据接纳口径。

## 主库与副本

| 位置 | 职责 |
| --- | --- |
| 主库 | 提供已发布的数据。每轮保存一条正式 Run 记录，管理状态、副本定位、主库基线和发布凭据，并保留运行历史 |
| 工作副本 | 保存候选市场数据、累计 selection、采集计划、Batch、Issue 和修复结果。使用相同的 Run ID 关联本库记录 |

同一时间只允许一个尚未接收或拒绝的 Run。通过主库事务和唯一约束占住这个名额。首次创建时使用 SQLite 一致性备份，副本放在受限目录。中断后继续同一个 Run 和副本，成功批次可以复用。

## Run 生命周期

| 状态 | 进入条件和后续操作 |
| --- | --- |
| 运行中 | CLI 创建 Run 或恢复中断的采集，然后在副本执行批次 |
| 已中断 | 采集未完成。人工可以恢复同一副本，或拒绝该 Run |
| 待修复 | 采集结束，有未处理的问题。人工或 AI 使用 CLI 核验和修复副本 |
| 修复中 | 修复命令取得执行权，在副本同一事务提交业务变更和处理结论。完成后根据剩余问题进入待修复或待发布 |
| 待发布 | 候选版本可以交给人工核验。人工通过 CLI 接收或拒绝。重新打开问题时回到待修复 |
| 发布中 | 人工接收后，发布命令取得执行权并准备合入主库 |
| 成功 | 主库发布事务已提交。保留本轮历史，下一轮可开始 |
| 已拒绝 | 人工明确拒绝候选版本。保留运行记录和拒绝理由，下一轮可开始 |

**人工通过 CLI 接收或拒绝前，Run 始终保留副本和活跃名额。** 人工可从待修复状态拒绝，无需先解决所有问题。没有问题的 Run 也需人工接收。采集 CLI 在候选版本已准备好时返回其状态和 Run ID，定时器再次触发时报告当前状态。人工审核可以跨进程、跨天和跨重启。

## CLI 并发与发布协调

涉及既有 Run 的 CLI 先从主库查询状态，并按 Run ID 定位副本。会改变状态的命令用带旧状态条件的更新取得执行权，成功后才执行。创建 Run 的唯一约束防止同时开启两轮，修复和发布的状态切换防止同时操作同一个副本。审核等待期间无需保持进程或持有锁。

`pnpm data ingest --to YYYYMMDD` 启动或恢复采集。`runs`、`issues` 和诊断导出可查看候选状态，明确区分候选版本与已发布数据。`issues repair` 按计划中的 Run ID 定位副本，预览和执行以该副本为准。副本缺失、状态不符或候选版本发生变化时，CLI 报告原因。整轮操作通过 `runs inspect RUN_ID`、`runs accept RUN_ID --expect-candidate HASH` 与 `runs reject RUN_ID --reason REASON` 完成，与单条 Issue 的 `accept` 区分。

**只在合入主库时沿用现有发布锁。** 先暂停接纳新的受保护请求和任务，等待正在使用旧版数据的研究、回测等业务结束，再写主库。前端维护状态继续由实际发布锁决定。等待超时则释放发布锁、保留候选版本，恢复业务后可重新发起发布。

## 接收、拒绝与恢复

- **接收**绑定人工核验过的候选版本，涵盖业务值与问题处理结论。取得执行权后再次核对候选版本和主库基线。基线至少包括市场 revision、影响发布的 selection 和 schema 兼容性。基线发生变化时保留副本并报告差异，待重新核验。
- **发布**只应用本轮采集和修复产生的最终差量，按业务键明确记录新增、更新及删除。副本安装固定业务表清单的 SQLite 触发器，记录变更键，随批次或修复事务提交。发布前固定候选版本，事务按日志逐页读取并重放差量。进入发布窗口前准备差量，主库在一次事务里提交市场变化、selection、本轮 Batch、Issue、IssueResolution 和发布凭据。主库市场 revision 按本轮实际市场变化更新。保留来源版本、原始 ID 和捕获时间，主库用户、会话、研究、策略和 Job 仍按在线业务独立写入。
- **拒绝**记录理由，释放活跃名额。被拒绝版本的数据及候选成功凭证都没有发布效力。已成功或已拒绝后，按清理规则处置副本文件。清理失败留待后续收尾。
- **中断**由人工确认原命令已结束后，通过 `runs recover RUN_ID --confirm-stopped` 恢复同一个 Run。采集可接着未完成批次进行，修复以副本已提交结果为准。发布提交结果不明时先查主库发布凭据。查到已提交则只收尾，否则保留候选版本供人工重试。副本缺失或损坏时报出具体原因，交维护者判断。

## 实现与验收

- 在 `ingestion` 拆分副本生命周期、现有批次采集、修复路由和统一发布。复用显式数据库作用域、现有业务键及 Prisma 差异写入，迁移由 Prisma 生成。
- 同步 CLI 帮助、状态接口、双语文案、修复 Agent Prompt 和运行说明。顶栏区分采集中、待修复、待发布和已发布，维护遮罩只跟随主库发布协调。
- 验证两条 CLI 同时抢占、跨天待审核、修复与发布互斥、人工拒绝、发布等待超时和各阶段强制中断。确认候选数据和修复记录在接收前留在副本，接收后共同提交，并核对主库在线用户写入逐值保留。
- 用正常增量和财报集中刷新两种规模测量副本创建、发布排空、事务耗时和磁盘峰值。发布事务过慢时重新评估差量写入方式。
