# Ingestion 副本采集开发计划

初始设计日期：2026-11-04。副本采集已投入使用；2026-11-10 的接收读写分离实现及验收记录见文末。

每个 Run 有一个工作副本。采集、核验和修复在副本进行，人工通过 CLI 接收后，才把这轮的最终变化一次发布到主库。等待审核时，研究、策略和回测继续使用已发布数据。

保留现有自然起点、历史 ETF Top 100 累计名单、批次事务及数据接纳口径。

## 主库与副本

| 位置 | 职责 |
| --- | --- |
| 主库 | 提供已发布的数据。每轮保存一条正式 Run 记录，管理状态、副本定位、主库基线和发布凭据，并保留运行历史 |
| 工作副本 | 保存候选市场数据、累计 selection、采集计划、Batch、Issue 和修复结果。使用相同的 Run ID 关联本库记录 |

同一时间只允许一个尚未接收或拒绝的 Run。通过主库事务和唯一约束占住这个名额。首次创建时使用 SQLite 一致性备份，副本放在受限目录。中断后继续同一个 Run 和副本，成功批次可以复用。

## Run 生命周期

| 状态 | 进入条件和后续操作 |
| --- | --- |
| 运行中 | CLI 创建 Run 或恢复中断的采集，然后在副本执行批次 |
| 已中断 | 采集未完成。人工可以恢复同一副本，或拒绝该 Run |
| 待修复 | 采集结束，有未处理的问题。人工或 AI 使用 CLI 核验和修复副本 |
| 修复中 | 修复命令取得执行权，在副本同一事务提交业务变更和处理结论。完成后根据剩余问题进入待修复或待发布 |
| 待发布 | 候选版本可以交给人工核验。人工通过 CLI 接收或拒绝。重新打开问题时回到待修复 |
| 发布中 | 人工接收后，发布命令取得执行权并准备合入主库 |
| 成功 | 主库发布事务已提交。保留本轮历史，下一轮可开始 |
| 已拒绝 | 人工明确拒绝候选版本。保留运行记录和拒绝理由，下一轮可开始 |

**人工接收或拒绝前，Run 始终保留副本和活跃名额。** 人工可从待修复状态拒绝，无需先解决所有问题。没有问题的 Run 也需人工接收。采集 CLI 在候选版本已准备好时返回其状态和 Run ID，定时器再次触发时报告当前状态。人工审核可以跨进程、跨天和跨重启。

## CLI 并发与发布协调

涉及既有 Run 的 CLI 先从主库查询状态，并按 Run ID 定位副本。会改变状态的命令用带旧状态条件的更新取得执行权，成功后才执行。创建 Run 的唯一约束防止同时开启两轮，修复和发布的状态切换防止同时操作同一个副本。审核等待期间无需保持进程或持有锁。

`pnpm data ingest --to YYYYMMDD` 启动或恢复采集。`runs`、`issues` 和诊断导出可查看候选状态，明确区分候选版本与已发布数据。`issues repair` 按计划中的 Run ID 定位副本，预览和执行以该副本为准。副本缺失、状态不符或候选版本发生变化时，CLI 报告原因。整轮操作通过 `runs inspect RUN_ID`、`runs accept RUN_ID --expect-candidate HASH` 与 `runs reject RUN_ID --reason REASON` 完成，与单条 Issue 的 `accept` 区分。

**准备阶段仅持有维护写者锁，合入主库时才取得发布锁。** 先核验候选版本和主库基线，在事务外读取、比较并准备全部变化；这期间正常业务继续读取旧版市场数据。准备完成并校验清单后，暂停接纳新的受保护请求和任务，等待已有读取结束，再写主库。前端维护状态继续由实际发布锁决定。等待超时则释放发布锁、保留候选版本，恢复业务后可重新发起发布。

发布事务根据准备结果和可用的隔离测量基准估算时限；无匹配基准时明确回退到 30 分钟。
普通审核事务仍为 120 秒，发布锁等待沿用原有配置。市场变化、诊断和发布凭据仍在同一个事务中
提交；发布失败继续整体回滚并保留待接收副本。

`pnpm data runs retry RUN_ID` 显式恢复待修复或已中断副本，沿用原目标和计划，只重新尝试未成功批次。命令按 Run ID 核对活跃副本，通过带旧状态条件的更新取得执行权。等待审核的定时调用继续返回已有副本状态。

数据状态弹窗向具备服务端发布权限的用户提供“接收副本”。管理员邮箱由 `JIXIE_ADMIN_EMAILS` 配置，API 的 `NODE_ENV=development` 也允许有效登录用户发布。界面先读取候选版本、目标和摘要，确认后带版本摘要调用受保护的接收接口；发布继续由 `acceptCandidate` 协调读者和事务。接口位于业务读取门禁之外，避免发布请求持有自身读取引用。

## 接收、拒绝与恢复

- **接收**绑定人工核验过的候选版本，涵盖业务值与问题处理结论。取得执行权后再次核对候选版本和主库基线。基线至少包括市场 revision、影响发布的 selection 和 schema 兼容性。基线发生变化时保留副本并报告差异，待重新核验。
- **发布**只应用本轮采集和修复产生的最终差量，按业务键明确记录新增、更新及删除。副本触发器记录变更键，随业务事务提交。固定候选后，在维护写者锁内、主库事务外逐页读取变更键及两边记录，比较并保存分块写入清单；批次、Issue、IssueResolution 也提前分页准备。清单校验完整后，主库事务仅核对执行权并回放清单，共同提交市场变化、selection、诊断和发布凭据。来源版本、原始 ID、捕获时间及用户独立业务数据保留。
- **拒绝**记录理由，释放活跃名额。被拒绝版本的数据及候选成功凭证都没有发布效力。已成功或已拒绝后，按清理规则处置副本文件。清理失败留待后续收尾。
- **中断**由人工确认原命令已结束后，通过 `runs recover RUN_ID --confirm-stopped` 恢复同一个 Run。采集可接着未完成批次进行，修复以副本已提交结果为准。发布提交结果不明时先查主库发布凭据。查到已提交则只收尾，否则保留候选版本供人工重试。副本缺失或损坏时报出具体原因，交维护者判断。

静态检查已完成：根级 `pnpm typecheck` 通过（含静态后端边界扫描、SDK 生成物一致性及全部工作区类型检查），本次变更文件 ESLint、Prettier 和 `git diff --check` 通过。新增测试已参与类型检查和下述行为验证。

- 清单成功、失败、取消均由执行者清理；拒绝和已发布重入也清理残留。人工 `recover --confirm-stopped` 仍需要维护者确认旧执行者停止，并增加维护锁保护及旧操作清单清理；不会自动检查 PID 或自动重试发布。
- 日志分别记录准备时间、发布锁等待时间、写事务时间、各表操作量与估时结果。每处理十万个变更键输出准备进度；不输出业务记录内容。

### 时限基准

默认基准保存在 `apps/api/src/ingestion/publication-budget-profile.json`，通过静态 JSON 导入随代码编译和发布；不再需要 `JIXIE_PUBLICATION_BUDGET_PROFILE` 环境变量。
文件通过 schema 校验，包含 `version=1`、测量依据 `evidence`、百分比 `bufferPercent`、最低时限 `minimumMs`、提交预算 `commitMs` 和 `tables`。
每个表档位包含 `model`、`maximumRows`、`indexCount`，以及 `insertMs/updateMs/deleteMs`、
`insertByteMs/updateByteMs/deleteByteMs`、`callMs`、`indexMutationMs`。这些是由隔离测量校准的增量成本，不应重复计费。
`maximumRows=null` 表示经测量选取的保守未知规模档位。表规模来自已有 `sqlite_stat1`，只是可能陈旧的近似统计；缺失时使用未知档位，不执行全表 COUNT 或 ANALYZE。
操作数量、分类字节数、Prisma 调用数和索引变动工作量在准备过程中统计；更新涉及任一索引字段时，保守按该表索引数计入。

预计时长为各项实测成本之和加提交预算，再统一乘以 `1 + bufferPercent / 100`，并应用最低时限。
任一有写入的表缺少匹配规模／索引档位时，或某类操作只有未经测量的零占位系数时，整轮明确回退 30 分钟；超出可表达的计时范围时在发布前报错，不静默缩短时限。
已完成下述固定字段样本的隔离测量与独立样本预算验证。维护者随后确认将该文件纳入代码库并作为默认基准；数值沿用测量结果，来源说明改为引用本设计文档。测量没有覆盖全部业务表、字段宽度和硬件环境，未覆盖项继续兜底。旧的 960.46 秒包含准备工作，不能直接用于该基准。

### 实际验证结果

- 6 个测试文件的 22 项回归验证通过；另外增加真实子进程 `SIGKILL` 验收并通过，共 23 项不同测试。强杀发生在主库事务首块写入后，验证未提交写入不生效、旧状态和清单残留、人工恢复清理及再次接收成功。
- 后端边界检查器的 36 项自测通过，静态扫描零违规；完整构建通过。Vite 保留已有非阻断的 chunk 大小提示。
- 1500 万条混合变化验收：500 万新增、500 万更新、500 万删除，另有 500 万不变记录。全部经真实发布函数提交并按数量和值核对。加上夹具参考数据，共发布 15,000,104 条变化。
- 大规模准备耗时 605.98 秒，发布锁等待 3.43 毫秒，主库写事务 1037.38 秒；发布总耗时约 1643.49 秒。进程 RSS 采样峰值约 344.72 MiB，临时清单约 1.74 GiB。准备的约 10 分钟发生在主库事务和发布维护窗口之外，写入本身仍约 17 分钟，不能据此宣称逐条更新已提速。
- 大规模纯操作块的回放测量中，约 500 万条更新累计 881.28 秒，新增累计 94.42 秒，删除累计 48.00 秒。测量包含参数处理及 Prisma 写调用；混合边界块归入剩余回放预算，并非数据库引擎单条 SQL 的纯执行时间。
- 由这份固定字段样本生成仅供验收的基准，再用独立 30 万条变化样本核对：预计写入 34.151 秒，统一增加 50% 余量后时限 51.226 秒，实际写事务 17.079 秒，全部断言通过。估算偏保守，尤其大样本的剩余回放成本并非小样本的准确常数；未把该样本基准自动启用为生产配置。
- 测量代码位于 `apps/api/tests/publication-measurements.ts`。通过 `JIXIE_PUBLICATION_MEASUREMENT_OUT` 保存资源／分段测量，`JIXIE_PUBLICATION_CALIBRATION_OUT` 导出固定字段夹具的实验系数；这些变量仅由测试使用。系数对未观测操作不提供泛化保证，实验文件不应直接作为任意生产任务的基准。
- 隔离测试库与子进程已收尾；日志、测量和实验系数保留在 `/tmp/jixie-publication-*-20261110.*`，未更改工作库或其环境配置。
