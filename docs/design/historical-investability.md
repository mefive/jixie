# 4.7-A · 历史股票池与可投资状态

> 2026-07-28 制定。对应 `ROADMAP.md` 4.7-A。目标不是把审计提示改成绿色，而是消除会污染
> 横截面研究和回测的身份重复、退市股元数据缺失与历史风险状态缺口。

## 1. 已确认的问题

2026-07-28 的全库审计与上游复核得到：

- `Daily` 有 5,790 个历史股票代码，`StockBasic` 只有 5,533 个当前上市代码，差 257 个；
- 257 个中 254 个是 Tushare 当前 `list_status=D` 的退市代码；
- 另外 3 个是证券代码承继：
  - `000022.SZ → 001872.SZ`，2018-12-26 生效；
  - `000043.SZ → 001914.SZ`，2019-12-16 生效；
  - `300114.SZ → 302132.SZ`，2025-02-17 生效；
- 三组旧/新代码在 `Daily` 中分别有 691、1,127、2,447 个重合交易日，收盘价逐日相同。
  这是同一证券被重复计入横截面的真实错误，不只是主表 join 不完整。

根因是 `stock_basic` 同步只拉 `L`，并且每次全表覆盖；历史行情按日期永久保留。Tushare 在代码
变更后把历史序列归到新代码，旧同步留下的旧代码行没有被回收。

## 2. 数据模型

### 2.1 `StockBasic`

- 保留当前证券代码为主键；
- 新增 `delistDate`；
- 同步 `L / D / P / G` 全部状态；
- 只有四种状态都成功返回后才在一个事务中替换主表，禁止部分成功覆盖完整主表。

### 2.2 `StockCodeChange`

保存经交易所公告确认的代码承继关系：

- `oldTsCode`：旧代码，主键；
- `newTsCode`：Tushare 当前使用的规范代码；
- `effectiveDate`：新代码生效日；
- `source`：可审计的来源说明。

表的用途是解释和约束身份迁移，不在每条热查询中动态 join。

### 2.3 `StockNameHistory`

保存 Tushare `namechange` 的时点区间，并做可审计的最小规范化：

- `tsCode / name / startDate / endDate / announcementDate / changeReason`；
- 主键为 `(tsCode, startDate)`；
- `startDate <= D <= endDate`（`endDate=null` 表示仍有效）时，该名称在 D 日生效；
- 风险状态从历史名称确定性派生，不把今天名称回填到历史。
- 同名且重叠的重复记录保留较晚生效行；不同名称发生重叠时，前一区间截到后一区间开始前一日；
- 对 `namechange` 从未返回记录的当前上市证券，以 `StockBasic.listDate` 和当前名称补开放区间。
  这是“从上市起未改名”的元数据兜底，不用于覆盖已有历史名称。

派生口径：

- `riskWarning`：名称以 `ST / *ST / SST / S*ST / PT` 等风险前缀开头；
- `pendingDelisting`：名称进入退市整理命名（例如以“退”结尾或以“退市”开头）；
- 原始名称始终保留，分类函数有 fixture 单测，新增命名形态必须显式扩规则。

## 3. 规范代码与一次性清理

存储层以 Tushare 当前规范代码为稳定证券身份。一次性清理脚本按 `StockCodeChange`：

1. 对每张含股票代码的市场表比较旧/新代码重合主键；
2. 行情与限价等业务列必须完全一致；`AdjFactor` 只接受不超过 0.1% 的上游精度修订，
   `DailyBasic` 只接受股息率空值回填或 0.005 的小数精度差；
3. `FinaIndicator` 同报告期可能在重组后追溯重述，重合时保留规范代码下较晚的供应商版本；
4. 旧代码独有行复制到新代码；
5. 完整性校验通过后删除旧代码行；
6. 清理前创建 SQLite 在线备份，清理后重跑全量数据审计。

这样研究序列连续且不会重复计数。历史成交展示使用规范代码；若未来产品需要展示“当时的交易代码”，
再由 `StockCodeChange.effectiveDate` 做显示层转换，不为当前需求扩展订单身份模型。

## 4. 同步

新增 `sync:stock-history`：

1. 同步四种状态的 `StockBasic`；
2. 按公告日期分段拉取 `namechange`，单段触及上游 10,000 行上限时递归二分；
3. 所有分段成功后规范化名称区间，并在单个事务中全量替换，保证失败不损坏现有表；
4. 最后校验每个有行情的规范股票代码都能关联主表，并检查当前股票是否有开放名称区间。

代码承继关系是小而低频的交易所事实，首批三条在仓库代码中维护并幂等 seed；审计发现新的孤儿代码时
必须先查明是退市还是代码承继，禁止按相似名称自动猜测。

## 5. 因子分析与策略

### 5.1 因子报告

- V1/V2 报告输入和结果保持不变；
- 新增 `AnalysisSpecV3`，在 `universe` 中冻结
  `excludeRiskWarning / excludePendingDelisting`；
- 新运行默认两项开启；
- 方法论面板新增两级样本数，旧报告仍明确显示这些过滤不可用；
- `variantKey / testKey` 自然包含 V3 新字段，旧报告不会被新口径覆盖。

### 5.2 策略 SDK

`BarRow` 增加只读时点字段：

- `name: string | null`
- `riskWarning: boolean`
- `pendingDelisting: boolean`

平台不替策略强制排除；用户通过 `Universe.where` 自主决定。SDK 注册表、Monaco dts、文档和 Agent
prompt 由既有单一来源机制同步，直跑与 isolate 双车道必须保持逐位一致。

## 6. 审计与验收

必须同时满足：

1. `StockBasic` 含非零 `D` 状态，且 `delistDate` 对退市股有合理覆盖；
2. `Daily` 历史代码无法解释的孤儿数为 0；
3. 三组代码承继在所有已接入股票市场表中不再同时存在；
4. 历史名称区间无同代码日期重叠，开放区间每代码最多一条；
5. 抽样交易日的 ST 状态与 Tushare `stock_st` 一致；不一致必须留报告；
6. V1/V2 金标准不变，V3 报告显示真实风险状态剔除数；
7. 引擎直跑 / isolate parity、API 单测、typecheck、全量数据审计和相关 E2E 全绿。

## 7. 本轮不做

- 2015–2019 `moneyflow / stk_limit / toplist` 的普通缺口回填；
- 复权因子异常逐条归因；
- 负净资产与长期停牌过滤；
- `dataRevision`、参数扫描、每日信号或新数据页面。

## 8. 2026-07-28 验收结果

- `StockBasic`：`L=5,533`、`D=338`；`Daily` 5,787 个代码中未解释孤儿和非规范旧代码均为 0；
- `StockNameHistory`：14,148 段、5,874 个规范代码，区间重叠、重复开放区间、当前上市名称缺口均为 0；
- 严格全库审计：5 pass、7 个既有覆盖 warning、0 error；
- Tushare `stock_st` 交叉验证：2024-01-31、2024-12-31、2025-12-31 三个截面中，
  当日有行情证券的 ST 缺失、误报与名称不一致均为 0；
- V3 EP 真实分析（2024–2025）：23 个调仓期，风险警示阶段 88,580 → 88,065，
  共剔除 515 个候选观测；
- API 213 项测试、全仓 typecheck、前端生产构建、专项页面 E2E 均通过。
