# 维护触发与发布锁设计

日期：2026-10-20。状态：已实施，等待人工代码审阅和行为验证，尚未部署。

目标：所有维护触发点遵守同一互斥协议；第一阶段继续服务用户；第二阶段能可靠阻止新工作、等待在途工作并原子发布。进程异常退出后不因数据库遗留 running 永久封站。

## 1 锁的职责

单机 Linux＋SQLite 继续使用操作系统 flock，不引入分布式锁或数据库租约抢占。建议采用一把维护互斥锁和一组发布锁，共三个固定锁文件：

| 锁 | 模式与持有者 | 持有范围 | 对用户影响 |
| --- | --- | --- | --- |
| 维护任务锁 M：`maintenance.lock` | 维护／部署协调器排他持有 | 固定目标、创建候选、准备、校验、发布或退出 | 第一阶段不阻塞用户；其他维护任务不能启动 |
| 发布意图锁 P：`market-publish-intent.lock` | 发布者排他持有；业务准入时短暂共享持有 | 发布者从准备全部完成到发布窗口结束 | 排他持有期间停止接收新的相关业务工作 |
| 市场访问锁 R：`market-access.lock` | 业务工作共享持有；发布者排他持有 | 业务从读取市场／覆盖需求到完成结果写入；发布者在正式回填期间 | 已有业务可完成；取得排他锁后才能修改正式市场数据 |

P 和 R 是一组：P 阻止新工作不断进入，R 证明已有工作确实退出。仅用 running 状态、任务数量或一次门禁检查，不能消除“检查后又开始”的竞态；仅用 R 等待排他锁，也不能单独保证新读者不会不断插入造成发布饥饿。

锁文件位于正式数据库唯一对应的数据目录，生产统一从正式数据库身份解析并校验，标准路径为 `/var/lib/jixie/`。不同触发点不得各自覆盖为不同路径；路径别名需规范化。同一正式库对应同一组锁，暂存库不能推导出另一套正式锁。

三个文件固定创建，运行期间绝不删除或替换，避免不同 inode 导致两个进程各自认为持锁。文件存在不代表持锁，PID、心跳及数据库记录只用于诊断。

## 2 业务操作如何进入

需要读取可变市场数据、计算并写回结果，或修改维护覆盖需求的操作，使用同一个准入协议：

1. 非阻塞获取 P 共享锁。失败说明发布窗口已开始，HTTP 返回可重试的维护响应，后台执行暂缓。
2. 在仍持有 P 共享锁时，非阻塞获取 R 共享锁；失败释放 P，退出并重试，不绕过锁执行。
3. 获取 R 后立即释放 P。R 共享句柄持续持有，覆盖实际工作和相关结果提交；成功、失败或取消后释放。

发布者必须先拿 P 排他锁，故不会出现“某请求通过门禁但尚未登记，发布者已认定无人运行”的空档。P 共享区间只包含加锁，不做数据库查询或业务计算。

| 操作 | R 共享锁覆盖范围 |
| --- | --- |
| 市场 HTTP 查询 | 一次请求中的市场查询、关联组装和响应结果确定；不覆盖客户端慢速下载时间 |
| Research Cell／全文运行 | 本次逻辑运行的市场读取、跨 Cell 计算和结果持久化，不覆盖编辑器空闲期 |
| Factor／Strategy 分析或回测 | 真正开始执行到结果提交；Worker 必须受同一持有范围保护 |
| Agent | 可能跨工具读取市场、生成或校验代码的业务轮次；纯私有历史展示不必持有 |
| Signals／账户重放／因子气象 | 本次读取市场、生成派生结果、业务 CAS 及结果提交 |
| 部署配置等覆盖需求变更 | 从校验依赖到提交配置，防止发布前复查后又改变所需证券集合 |
| 登录、健康、状态查询、纯私有内容编辑 | 不因本方案获取市场锁；其自身权限和事务规则保持 |

长期 SSE 订阅、浏览器连接和空闲 Python 会话不持有 R。排队 Job 不持有 R，开始执行时才申请；拿不到锁则保留待执行状态，不能错误标成业务计算失败。长任务超过发布等待预算时由发布者退出本次窗口，不为抢发布强行终止用户工作。

API、后台调度器和 CLI 都要接入；只给 HTTP middleware 加锁覆盖不了后台消费。业务准入必须在第一次相关数据访问前完成，不能计算中途才补锁。

## 3 维护发布的完整顺序

```text
取得 M
  → 第一阶段：复制所需市场数据、下载、修复、计算、审计
  → 关闭候选写者，冻结候选和变更清单
  → 取得 P 排他：阻止新相关工作进入
  → 有限等待 R 排他：已有工作继续完成
  → 检查基线、需求指纹及发布身份
  → 一个正式事务回填变更、水位、凭据、后续动作
  → 确认提交或回滚，释放 R，再释放 P
  → 释放 M
  → 独立执行发布后任务
```

第一阶段只有 M，不获取 P／R 排他。历史错误、下载失败、审计失败均保留诊断和断点，释放 M 后等待重试，不影响已发布数据访问。

取得 R 排他后再读取当前需求指纹，可防止需求复核与提交之间的新配置变更。基线或需求不满足时不进入回填：先释放 R／P，再回到准备；不能持发布门禁进行下载、重算或等待外部服务。

发布事务只使用冻结候选，按业务清单回填。事务提交／回滚确认前不释放 R／P；提交响应不明时优先查询正式发布身份，不能重新提交来猜测。发布后缓存和持久 Python 会话在下次使用前校验 dataRevision，防止旧内存输入与新正式数据混用。

## 4 各触发点统一规则

| 触发点 | M | P／R | 冲突与重试 |
| --- | --- | --- | --- |
| systemd daily／weekly | CLI 启动器获取并全程持有 | 仅全部 ready 后排他获取 | M 冲突立即退出 75，由现有服务重试策略再试；不能先改运行状态或候选 |
| 人工 daily／weekly／repair | 与定时任务完全相同，不允许直接绕开启动器 | 同一发布协议 | 返回当前持有者诊断；人工可稍后重试，不强行接管 |
| repair 默认范围／首次初始化／resume-only | 统一使用 M；恢复旧候选也先获锁 | 同一发布协议；无有效基线另显示未就绪 | 先核对候选、baseDataRevision 与 schema，不凭断点直接续写 |
| 独立 Market sync／代码归一 | 已上线正式库不允许裸写；转交维护协调器，获取 M | 通过候选校验后发布 | 不能仅在旧 CLI 外包 flock 后继续直接写正式市场表；查询／帮助不加 M |
| import:data | 无已发布基线时获取 M，作为显式初始化；上线后走候选维护 | 初始化完成的数据和首次水位通过发布提交 | 子步骤不能重复获取同一个 M；默认拒绝上线库直写导入 |
| bootstrap／正式迁移 | 获取同一个 M，迁移／停机前排他取得 P、R | 持有到数据库和兼容 API 可用；保留 deploy 自身恢复规则 | 无法获锁则拒绝切换；不得绕过 M 抢跑迁移 |
| 部署激活初始化 | 部署步骤释放已有 M 后，再由统一入口获取；或显式由同一协调器持有 | 同初始化协议 | 不能父进程等子进程结束，子进程却等待父进程持有的 M |
| signals:run | 市场准备部分转交 M 协调器；不再直接同步正式市场表 | 发布结束后信号只获取 P 共享准入及 R 共享 | 数据未准备好先退出信号执行，不能持 R 再请求 M |
| API／Job／Research／气象触发 | 普通计算不获取 M，不得自行写正式市场表 | 采用第 2 节共享准入协议 | 发布时暂缓；独立业务认领／CAS 仍负责同对象并发 |
| 发布后任务重试 | 不获取 M，使用已提交的发布身份 | 需要市场数据时持 R 共享 | 校验目标与实际输入修订；不能悄悄在另一版本上执行却标记原输入成功 |
| 候选清理 | 独立清理进程先获取 M，确认目标无活动写者 | 不获取 P／R 排他 | 拿不到 M 就延后；不得清理正在准备或发布的目录 |

M 一直由正式协调器持有，暂存 Worker 不独立获 M，不做正式发布。所有公开 CLI 入口及源码／编译入口使用同一个受控启动器，数据库资源只有获锁后才打开或开始工作；不能只在 package.json 的某一个命令外包一层锁。

后续任务在释放 M 后执行，市场修订可能已变化：若输入必须是特定修订而当前已不同，按业务规则重建／重新调度或记录被新运行替代；不得伪称旧版结果，也不能只因尚未执行就无限阻止下一轮维护。已执行的共享任务会由下一次发布等待 R 结束。

## 5 持锁真实性与死锁约束

| 问题 | 约束 |
| --- | --- |
| 仅检查 LOCK_HELD 环境变量 | 移除其作为授权依据。变量可作诊断，但持锁能力必须对应启动器持有的实际句柄／受控会话和正式库身份 |
| 锁实现保持 TS 技术栈 | 业务与句柄生命周期由 TS 管理，不新增 Python 持锁程序。已确认采用 `fs-ext` 原生 flock 绑定；业务逻辑保持 TS，Ubuntu 安装时需要 C/C++、make 和 node-gyp 使用的 Python 3，编译产物必须匹配目标平台与 Node ABI。macOS 开发环境也必须支持真实 OS 锁，不允许用无锁或文件存在检查替代 |
| 重入与嵌套命令 | 嵌套步骤显式复用同一协调器上下文，不重新打开锁文件再抢锁；不凭手写 env 跳过验证 |
| 取锁顺序 | 发布者固定 M → P 排他 → R 排他；业务固定 P 共享 → R 共享 → 释放 P。禁止逆序 |
| 共享升排他 | 不允许持 R 共享时升级发布、请求 M 或等待另一个需要发布的任务；先结束当前操作并释放，再走维护入口 |
| 排队任务等待 | 发布者不等待所有 queued Job 结束，只等待真实持有 R 的执行。后续消费者在窗口结束后再准入 |
| 锁句柄复用 | 逻辑操作必须有明确生命周期；同进程共享底层句柄时正确计数，不得一个请求退出就释放其他任务仍依赖的锁 |
| 父子进程 | 按明确执行树管理，禁止锁句柄无意继承。主协调器终止时停止并等待暂存写者，恢复前确认旧写者消失；暂存 Worker 不得持正式发布连接 |
| 超时 | M 非阻塞获取；P 的排他获取和 R 排空都必须有期限。超时完整释放本次已得发布锁，不无限封站 |

若使用本地锁辅助进程，其锁必须绑定调用方连接／生命周期；调用方异常退出后结束其锁会话，不得留下独立常驻持锁孤儿。锁故障、身份不匹配明确失败，不能自动降级为无锁运行。具体进程／句柄验证方式是实现前必须审阅的工程项。

对正常业务而言，取得 R 后才检查／使用对应市场修订；运行结果的去重、任务认领、成交修订和账户 generation CAS 继续生效。M／R 不替代这些业务并发规则。

## 6 异常恢复与状态查询

| 故障 | 恢复规则 |
| --- | --- |
| 准备进程异常退出 | M 随持有者退出释放，清理／回收旧候选写者后续跑；没有 P 排他，不封站 |
| 发布排空超时 | 不写市场数据，释放已得 P／R；M 可留给本轮继续准备，也可释放等待重试 |
| 发布事务失败 | 回滚确认后释放 R、P；用户继续读取旧版 |
| 发布者被杀 | 连接退出后由 SQLite 完成提交或回滚；OS 锁随真实句柄关闭释放。恢复依据正式凭据，不依据遗留 publishing |
| 提交成功但后续未调度 | 正式库读取发布凭据及动作记录，幂等补执行，不重复市场发布 |
| API 重启 | 不把启动前全部 running 都假定死亡；各运行必须核对真实执行者及业务认领，特别是另一个 CLI 的气象／Job |
| deploy 中断 | 数据库迁移、应用兼容性可能未完成，按 deploy 专属恢复协议判断，不能因锁空闲就宣布部署成功 |

`GET /api/maintenance/status` 区分任务进行、发布窗口和业务失败。数据维护造成的 `active` 只对应实际 P 排他持有的发布窗口；不能根据 M、历史 running/error 或心跳过期封站。首次无基线、数据库技术不可用及 deploy 状态另外表达，不从暂存审计错误自动生成这些状态。

状态接口观察锁只是展示；真正业务准入必须实际获取共享锁。先查 active=false 再执行仍有竞态，不能作为安全入口。

## 7 验收重点

- 定时维护、人工 repair、sync 转交、导入、部署和清理同时争抢 M，实际只准一个协调器进入，路径别名不能绕过。
- 准备阶段任意失败不取得 P 排他，用户请求保持可用；候选恢复不复用旧写者仍在修改的文件。
- 在“通过门禁、尚未持 R”的边界并发发起发布，验证共享准入协议没有空档。
- 发布意图持有时不再启动新任务；已有任务完成才允许回填；queued Job 不使排空永久等待。
- 长任务导致排空超时，全部本次发布锁释放，旧版继续可用，无数据部分回填。
- 配置需求变更与发布竞态被 R 协议覆盖，复核后的输入要求不能在提交前变化。
- 在发布前、事务中、提交后杀进程，验证锁／连接释放、凭据判定及后续幂等恢复；不靠改 running 解封。
- 父子进程、API 重启、锁辅助能力退出、锁文件权限及句柄继承均有独立故障用例。

本轮使用 TS＋fs-ext 落地该协议；未新增数据库模型或迁移。协议元数据、发布凭据和待处理动作写入既有 MaintenanceRun.summary。人工代码审阅前只做静态检查，之后再做并发与故障验证。
