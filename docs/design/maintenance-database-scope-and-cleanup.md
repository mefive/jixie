# Maintenance 数据库作用域、进程与清理

日期：2026-10-22。状态：设计与修订代码均获确认，必需验证通过，按已批准的提交信息交付。

计划提交：`refactor(maintenance): scope database access and reclaim run artifacts`。

## 1 目标与边界

维护准备继续使用完整市场候选库，发布继续使用已验证差量和正式事务凭据。把数据库选择从进程环境和
全局 Prisma 的 maintenance 判断中移到执行入口，取消仅为数据库隔离和 CLI 调度设置的子进程；统一
候选生命周期与清理，回收不再使用的 owner 锁文件。不改变市场数据 schema、同步口径、计算公式、审计
门槛、公开 SDK 或 HTTP 契约，不执行真实维护或直接清理现有真实数据作为开发验证。

候选调用链及同步 CLI 的文件级静态盘点发现 78 个直接使用全局 Prisma 的文件：Maintenance 9、Market
业务及财报 Worker 44、Market CLI 24、Signals 取数适配 1。这不是最终修改文件数；入口、共用调用方及
测试也需检查。数据库作用域替代逐函数传递 Prisma，不引入通用依赖注入容器。

## 2 数据库基础设施

提供 `createDatabase(url)`、`withDatabase(database, operation)`、`getDatabase()`。以 AsyncLocalStorage
保存本次异步执行的数据库绑定；没有有效绑定时明确报错，不默认回退主库。嵌套退出恢复外层绑定，不
修改全局变量、DATABASE_URL 或工作目录。业务在函数执行时获取连接，不在模块顶层缓存作用域连接。

主库实例仍按应用进程复用，由 API、Job、Worker、CLI 等边界绑定。Maintenance 协调器在主库作用域中
创建候选客户端，进入候选作用域执行下载、补缺、计算及审计。正式控制记录通过明确的正式连接更新；
候选自己的工作流记录、checkpoint 和预期水位保持原语义。正式发布继续使用独立事务客户端。

作用域不拥有客户端；创建者在所有任务、进度和心跳结束后关闭连接。事务仍显式使用 transaction 参数，
不增加隐式事务传播。运行上下文失效后，继承了旧上下文的延迟任务应拒绝访问。数据库模块不认识
maintenance、staging、业务锁或父子进程。

运行身份、固定时间、日期上限、冻结部署需求、进度及待执行动作由维护自己的执行上下文管理。正式需求
在协调器冻结并在发布前复核，候选不得隐式回读正式用户表。准备只记录 Signals／气象动作，不实际运行。

## 3 进程边界

| 现有进程 | 目标 |
| --- | --- |
| 候选准备 | 改为协调器内调用 |
| 最终计算／审计 | 改为协调器内调用 |
| import 单项同步启动层 | 改为具名同步函数；CLI 只处理输入输出和入口生命周期 |
| 财报／财务指标／分红批次 | 保留，每次一个，由协调器直接管理，退出回收原生内存 |
| 正式发布后 Signals、气象和沙箱 | 保持独立业务执行设施 |

常规 daily／repair 不再创建业务子进程；weekly／import 只在财务批次需要时创建一层子进程。
Prisma 实例不跨进程传递；财务子进程接收候选身份和路径，创建并绑定自己的候选连接。逐项持久确认／ACK
保留。同步函数不得自行修改 process.argv、导入自执行 CLI 或关闭调用者的连接。

## 4 锁与退出

候选不再使用 `owner-<candidateId>.lock`。M（maintenance.lock）覆盖候选准备、计算、审计、发布和
清理。财务子进程通过 stdio 继承同一加锁文件描述符，核验真实文件身份；环境布尔值不是所有权证明。
M 持有者只关闭自己的描述符，不提前显式 unlock 共享的 open-file description。最后持有者退出后才
释放 M；父进程被杀而子进程仍写候选时，其他维护／清理不能进入。正常发布前必须等待批次进程退出，
停止心跳／回调并关闭候选连接。无法确认写者结束时不能发布、清理或继续释放门禁。

P、R 继续负责正式市场访问准入及短暂发布窗口，不在下载准备期间排他。部署继承 M 的路径和退出规则
必须同步检查，不能由 Shell 显式 unlock 提前破坏后代的所有权。

Job、Agent、气象及发布后处理仍有独立 owner 锁。获取 owner 锁后核验句柄与当前路径的 dev/inode 一致；
已被删除或替换时关闭旧句柄并重新竞争。正常释放及遗留扫描仅在取得排他锁并核验身份后 unlink，文件
删除期间保持排他，活动持有者跳过。固定 M/P/R 文件不删除，符号链接和不明文件不清理。

首次启用新回收规则前，必须停止旧版本 API、CLI 及后代，再启动新版本。旧进程不具备文件身份复核，
新旧协议混用不安全。该条件属于升级约束，不等于开发时授权停止用户进程。

## 5 候选清理政策

| 状态 | 政策 |
| --- | --- |
| 明确数据获取失败且候选仍有效 | 保留断点 |
| ready，发布未提交且仍有效 | 保留，只重试发布 |
| 计算、审计、程序错误 | 保存诊断后清理 |
| 中断且既无有效 ready 也无明确下载失败记录 | 保存诊断后清理 |
| 正式基线、schema、规则或冻结需求变化，候选失效 | 保存诊断后清理 |
| 正式凭据确认已发布 | 清理，不等后处理成功 |
| 无法确认发布结果、记录或目录归属 | 暂缓并报告 |

下载失败按结构化来源错误识别，不按错误文案或最后进度阶段猜测。响应映射／程序错误不冒充来源等待。
财务 Worker 错误分类须跨 IPC 保留。确认提交前后以正式凭据为准，不凭本地文件或退出码重复发布。

诊断、原目标和重建依据先持久化，删除后单独记清理结果；不把失败改成功，不覆盖后处理 stage。删除失败
可重试，不阻断新维护。重建沿用原目标时间和参数，不因清理悄悄扩大日期范围。旧协议已标记 stage=abandoned 的历史运行不重新入队；新回收保持原 stage，以 replacementId 原子关联重建记录。

范围限定为归属明确的候选运行目录：candidate.db 及其 SQLite 附件、变更文件、清单、需求、动作和审计。
正式库、备份、迁移、固定锁、外部 /tmp 报告不属于候选清理。判断先比较元数据，不为清理扫描大型数据库。

维护开始及结束复用同一清理实现。`pnpm maintenance cleanup` 默认只展示计划、原因和大小；
`pnpm maintenance cleanup --apply` 执行清理并补收 owner 遗留文件，不触发数据下载、计算或后处理。

## 6 审阅与验证

实现完成后仅运行静态检查：工作区 typecheck（含边界静态扫描及生成物一致性）、相关 ESLint／Prettier、
Shell 语法和 diff 检查。测试、构建、运行探针在人工审阅通过后执行。

行为验证覆盖：

- 无绑定拒绝、嵌套恢复、并发主／副本隔离、失效上下文、API／Job／CLI／Worker／测试入口绑定；
- 正式与候选填入不同数据，验证下载／计算／审计不串库，发布前正式市场和用户记录不变；
- 同进程连续同步、错误传递、固定目标与需求、心跳回收、连接收尾、候选计算结果一致性及内存观察；
- 数据获取失败恢复、审计失败清理、ready 发布重试不重新下载、提交结果不明、发布后动作独立恢复；
- 父进程被杀而财务写者存活时 M 保持、正常退出释放、源码／编译财务 IPC、部署继承 FD；
- owner 文件打开／删除／重建竞态、多共享持有者、崩溃、符号链接、清理中断与幂等重试。

若去掉外层进程后内存显著累积、无法证明数据库作用域或锁生命周期隔离，回到方案审阅，不静默回退主库、
降低审计或跳过测试。全部验证使用隔离数据与来源替身，结束后清理测试进程和连接。
