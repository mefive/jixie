# 采集并发设计

日期：2026-11-07。状态：已实现，静态检查与行为验证通过。

## 1. 方案

采用 **有限并行下载，按原计划顺序准备并串行入库**。先从 4 个下载任务开始；批次范围、PIT、完整响应和成功收据规则沿用现状，不为并发增加月／年切片。

固定计划 → 并行下载原始响应 → 有界缓冲 → 读取当前库并准备 → 单批事务提交。

目前有两层串行：Ingestion 逐批执行；TushareClient 也串行请求，并在响应结束后再等待至少 800ms。两层都要调整，单纯给现有批次套 `Promise.all` 无法提速，还可能提前读取过期的业务上下文。

## 2. 哪些可以并发

| 工作 | 下载方式 | 必须守住的边界 |
| --- | --- | --- |
| 日历、股票／ETF 目录 | 前置阶段保持现有顺序 | 依赖它们的计划生成前，先完成提交 |
| ETF 历史选取 | 不同日期可并行 | 按日期提交名单并集；选取完成后固定本轮名单，再规划 ETF 历史 |
| 行情、复权、估值、限价、名称、指数权重 | 批次间可并行 | 来源各自独立；快照仅替换自己的精确范围 |
| 财报、财务指标、分红 | 批次间可并行下载 | 既有版本、分红身份和修订合并所需的查库与准备，移到串行提交端 |
| 同一批次的分页、新旧证券代码查询 | 批内仍顺序执行 | 所有响应完整后才允许提交；每次 HTTP 都参与限流 |

**下载完成顺序不决定写入顺序。** 后面的批次可以先下载完，但要等前面的批次提交或明确失败，再基于最新库内容准备；失败批次记录结果后继续后续工作。这样保留同证券、同事件和同报告期的现有合并顺序。

## 3. Tushare 限流

官方当前说明如下，核对日期为 2026-11-07：

| 积分档位 | 每分钟频次 | 每日总量 |
| --- | ---: | --- |
| 120 | 50 | 8,000 次，仅非复权日线 |
| 2000 以上 | 200 | 每个 API 100,000 次 |
| 5000 以上 | 500 | 常规数据无上限 |

来源：[积分与频次表](https://tushare.pro/document/2?doc_id=290)。特殊接口另有独立额度；该表未明确统一的并发连接上限，也未充分说明所有额度是否跨 API 合并。因此采用**账号总预算＋单 API 预算**的保守控制，不能给每个下载任务各配一份额度。[日线文档](https://tushare.pro/document/2?doc_id=27)也明确列出 5000 积分档每分钟 500 次、每次 6000 行；行数上限与频次是两回事。

执行规则：

- **并发数与频次分开。** 初始并发 4，频次先沿用全局 75 次／分钟、发起间隔至少 800ms；改为从请求发起时计间隔，允许前一次响应尚未结束。核实当前账号与接口额度后，可配置为 200 档取 180 次／分钟，500 档取 450 次／分钟，并继续服从更低的接口额度。这些折扣是本项目的余量，不是官方要求。
- 共享一个发送调度器，按滚动 60 秒计数并平滑发起。分页、满页探测、失败重试都计数；等待额度不占 HTTP 连接，真正发送前原子占用额度和连接槽位。
- 同 token 的本项目发送进程通过共享锁互斥，进程内所有请求共用预算。配额账本放在私有采集目录，发送前持久化预占，跨 Run 和重启保留，不保存明文 token。有日上限时按滚动 24 小时保守控制；其他机器或外部工具使用同 token 时，需预留它们的预算。
- HTTP 429 优先遵守 `Retry-After`，缺失时共享冷却至少 60 秒；网络／5xx 指数退避加抖动，最多重试 2 次，重试重新申请额度。Tushare 业务拒绝仅对已核实的限流错误分类处理，参数／权限错误不重试，不依赖猜测错误文案。

当前账号的实际额度尚未核实；获得 VIP 数据不能替代逐接口核对。等待限流、冷却和退避都必须可被暂停信号取消。

## 4. 调度与资源

由一个协调器管理计划、批次状态、诊断和数据库写入；下载任务只返回原始响应、请求记录及真实抓取时间，不直接修改共享计划。每批使用独立诊断上下文。每次 HTTP 记录真实发起／返回时间，覆盖证据和捕获时间分别据此计算，与排队、入库时间分开；网络和等待期间不持写事务。

同时最多 4 个 HTTP 请求，最多 8 个已派发但未提交的批次；缓冲按响应字节再设高水位，初值 64MiB，达到后停止继续预取。超大响应临时落盘，不为内存压力重新按月／年切片。顺序最靠前的待办始终预留一个下载槽位，避免后面的响应占满缓冲、前面的批次却无法继续下载。

满页拆分仍由协调器在同一事务保存 `split` 收据和子计划。子区间继承父批次的位置、优先于其后的批次执行，且互不重叠；并发下载任务不能各自覆盖 `scopeSnapshot`。同一次执行中，一个逻辑单元只派发一个在途尝试，网络重试留在该尝试内部；中断恢复为未成功单元新增尝试。

## 5. 暂停、强杀与恢复

恢复依据始终是**业务数据与成功收据的提交事务**，下载完或临时文件存在都不代表成功。

| 停止位置 | 处理与恢复 |
| --- | --- |
| 尚未派发、等待额度 | 不创建虚假的失败尝试；恢复后正常派发 |
| 下载或分页中 | 取消整个批次，保留已发生的请求诊断；恢复时整批重下 |
| 已下载，等待准备／入库 | 丢弃未提交结果；临时文件不作为续传凭证，恢复后整批重下 |
| 已进入写事务 | 让这笔事务完成或回滚；数据、问题、收据和 revision 共同进退 |
| 已提交，尚未汇总 Run | 成功事实已经成立；恢复时跳过，不因汇总缺失重复下载 |
| 正在保存拆分计划 | 父收据和子计划共同提交或回滚，恢复后只执行已保存的计划 |

收到暂停信号后先关闭派发入口，取消网络及等待中的任务，清空未提交缓冲；等待下载任务退出和写事务确定后，才汇总并标记 Run 为 `interrupted`、释放执行权。不能先释放执行权，再让旧任务迟到写入。正常暂停不制造待人工修复的来源错误。

强杀后沿用现有人工确认旧进程已结束的恢复机制，把遗留的 `running` 尝试标为中断。继续同一 Run、副本、目标和成功批次；已有串行计划也可使用新调度器，不重建成功财报。每次重新下载使用新的实际捕获时间；单元已有的范围和证券准入边界保持固定。

## 6. 实施与验收

主要改动在 `ingestion/ingest.ts` 的调度与提交、`market/synchronization` 的下载／准备分离，以及 `providers/tushare` 的统一限流。配额账本属于执行元数据，成功覆盖仍只认现有批次表；不改变市场数据 schema、PIT 或候选发布流程。

验收覆盖：并发请求上限与限流窗口；分页和重试计数；响应乱序下结果一致；两个分红批次命中同一事件；拆分不会覆盖其他计划或卡死；上表各中断位置恢复无半批、无重复接纳；旧 Run 成功批次继续跳过。

保留批次总耗时，补充限流等待、下载、待入库和准备／写入耗时，以及真实 HTTP 次数。用固定响应和时钟分别验证并发 1／2／4 的业务值、版本指纹与诊断一致；再测真实吞吐。吞吐由网络、额度和串行准备／写入共同限制，整轮看墙钟用时，各批耗时用于定位瓶颈。

现有规则参见：[采集设计](ingestion.md)、[副本生命周期](ingestion-replica-plan.md)。


## 实现约定

计划提交：`perf(ingestion): prefetch batches with shared rate limits`。用户已授权本次自主验证、提交并恢复原 Run。

CLI 默认并发 4；注入自定义 source 的业务调用未指定并发时保持 1，可显式选择 1～4。实际 HTTP 另由共享限流器控制。原始响应按请求顺序缓存并回放给现有准备入口，回放不访问网络；这使领域字段及映射继续只有一套实现。

无需数据库迁移。`IngestionBatch.request` 新写入 `{ version: 2, requests, execution }`，旧数组继续读取；`runs inspect` 默认返回 `execution`，旧批次为 null。覆盖证据使用真实 HTTP 开始时间，队列和写入时间不冒充捕获时间。只有业务数据、问题、终态和 revision 的原有事务提交才证明成功；完整写入耗时在事务后补记，中途退出时该项可以为 null。

配额预占追加到私有 JSONL 并 fsync 后才允许发送，账号锁由 flock 持有；只丢弃尚未发出请求的残缺尾记录，内部损坏拒绝发送。每小时及启动时原子压缩为最近 24 小时，保留冷却期限。临时响应在正常退出时清理，恢复时只回收已取得执行权的同一 Run 遗留文件。


验证：72 个相关测试文件共 376 项通过，覆盖并发 1／2／4 的财报版本指纹、修订质量和分红合并一致性，响应乱序、满页拆分、落盘、暂停恢复、配额持久化、账号互斥、429 冷却与取消。根级类型／边界／生成物检查、ESLint、格式和构建通过。正常收尾会把未提交尝试直接标为 interrupted；旧批次 execution 返回 null。测试使用隔离库和模拟来源，未启动临时服务。
