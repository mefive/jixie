# 维护暂存数据库与原子发布设计

日期：2026-10-20。状态：已实施，等待人工代码审阅；尚未运行行为验证或提交。

采用独立暂存 SQLite，复用现有 Prisma schema 和迁移，**只复制本轮所需市场表及依赖范围的数据，发布时只回填已验证的变更清单，不整库或整表复制。** 维护分为两个阶段：暂存准备不阻塞主库，全部校验通过后才进入正式发布窗口。baseline 修复合并到 repair，不再设计独立修复入口；首次发布水位初始化仍由 `daily --initialize-only` 负责。

## 1 维护入口

| 入口 | 职责 | 目标范围 |
| --- | --- | --- |
| `daily` | 补齐日常市场数据，检查历史尾部，修复并重算指标 | 本轮连续待补交易日及关联历史影响范围 |
| `weekly` | 更新低频参考数据、修订历史、整体审计与重算 | 固定周目标及其历史影响范围 |
| `repair START END` | 人工修复指定历史区间 | 指定日期区间及受影响的派生结果 |
| `repair` | 按需检查、补齐近期历史，承接原 baseline 修复用途 | 默认最近 20 个已完成交易日 |
| `daily --initialize-only` | 验证导入数据并建立首次发布水位 | 首次基线，不自动继续追到今天 |
| `daily --resume-only` | 恢复原目标，不创建新目标 | 原运行的未完成准备、发布或后续任务 |

`repair` 默认按需补缺；需要重新获取已有数据时使用显式刷新选项，参数为 `--refresh`。两种范围共用运行记录、断点、候选库、审计和发布协议，不保留另一套 baseline 执行链。

日水位表示数据已连续发布到哪个交易日。repair 更新历史数据时增加修订号，但不倒退或越过未验证日期推进日水位。首次初始化可复用 repair 的内部补缺能力，修复结果与首次水位在同一次发布事务中提交，不嵌套另一轮正式发布。

`deploy` 是部署停机维护，保留独立规则，不纳入本设计的数据维护自动恢复逻辑。

## 2 两阶段流程与访问原则

| 阶段 | 做什么 | 主库与访问 | 失败后 |
| --- | --- | --- | --- |
| 第一阶段：暂存准备 | 一致性快照、下载、历史检查、修复、派生计算、审计、保存断点 | 不改正式市场数据，不建立阻塞门禁；用户继续使用已发布数据 | 保留候选及错误，按断点重试；不自动封站 |
| 第二阶段：正式发布 | 建立发布门禁、等待在途操作、事务合并市场变更及发布记录 | 此时才暂停新的跨版本业务操作 | 事务回滚后解除本次门禁，继续使用旧版；提交结果不明时先核对正式发布凭据 |
| 发布后处理 | 信号、账户结算、因子气象、通知 | 正常访问已发布新版 | 独立重试，不撤销市场发布、不封站 |

**第一阶段即便发现历史错误、无法修复、下载失败、审计失败或进程崩溃，也不得据此把主库切入阻塞维护状态。** 问题作为诊断与重试依据保留，不从候选审计结果自动推导全站不可用。

维护“正在运行／失败”与“用户访问受阻”分开表示。正式库可以写入维护进度和断点等控制记录，但这些记录不影响第一阶段的访问许可。

首次没有已发布基线时仍显示数据未就绪；这是初始化状态，不是准备失败触发封站。当前旧流程可能已经部分修改正式数据，切换新协议前需处理这些遗留记录，不能直接套用新规则解封。

## 3 暂存库与连接

独立暂存库避免给每张业务表加版本过滤，也不需要手写同结构暂存表。改动主要集中在连接隔离、Worker、发布合并与恢复；是否比其他方案总成本更低，仍需测量数据规模和发布时间。

| 对象 | 内容与职责 |
| --- | --- |
| 正式库 | 对外数据、用户数据、维护控制记录和正式发布凭据 |
| 暂存库 | 同一正式读快照中的所需市场数据，以及本轮候选变更，支持历史查询和滚动计算 |
| 运行目录 | 候选身份、变更清单、校验摘要和内容哈希 |
| 正式协调器 | 连接正式库，管理运行、断点、锁、发布与清理 |
| 暂存 Worker | 独立进程连接暂存库，执行市场准备、计算与审计；子进程继承该连接 |

暂存库使用同一份 schema 和迁移建立表结构，不手工维护第二套表定义。每个工作流显式列出所需市场表和行范围，包含下载、历史修复、滚动计算及审计的间接依赖；必要时可以读取整张依赖市场表，但不是默认复制整个正式库。新增依赖必须同步更新清单，缺依赖时明确失败。

各表数据通过同一个正式数据库读快照分批复制，记录 baseDataRevision、schema／规则指纹和复制范围；复制完成前不能使用该候选。不能逐表开启互不关联的快照，也不能直接复制活跃 WAL 模式下的单个 `.db` 文件。schema、代码或计算规则改变后，旧候选不得直接续算。

不复制用户、会话、研究、策略、任务、成交及账户表。部署引用等业务需求由正式协调器从主库读取，提取为本轮明确输入，发布前复核指纹；暂存计算不能隐式回读主库。运行目录保持私有，目录 0700、文件 0600，不对外提供或上传。

暂存进程启动前设置并校验专属 `DATABASE_URL`，再导入现有全局 Prisma。不得运行中切换父进程地址，也不得连接失败后回退正式库。财报 Worker 等子进程遵守同样规则。

暂存进程禁止启动 Job 消费器、Agent、邮件或通知。维护控制状态始终由正式协调器管理，不从候选复制或恢复运行记录和水位。

## 4 各业务的准备与发布规则

所有下载、历史检查、修复、计算和审计都读取同一个候选基线。任一必需单元未完成，整轮候选不发布；失败单元重试，已验证断点可复用，主库保持原样且不阻塞。

| 业务 | 数据与断点粒度 | 成功发布规则与特殊限制 |
| --- | --- | --- |
| 日历与证券资料 | TradeCal、股票／ETF／期货基础资料、代码与历史名称；按来源、交易所、证券及区间 | 日历也在暂存库更新；保留生效历史，部分响应不删除未返回证券 |
| 股票行情及扩展 | Daily、AdjFactor、DailyBasic、StkLimit、Moneyflow、TopList；数据集＋交易日 | 同日必需切片及相关指标一起发布；合法稀疏／空结果按业务规则判断 |
| ETF 日更与历史恢复 | 日线、复权、份额；日更按证券／日期，历史按证券／年份／数据集 | 补缺只插缺键，修订只更新实际覆盖键；来源缺失观察不当作完整证明，不无限跨运行复用 |
| 指数与行业 | 行情、估值、权重、历史成员；按指数／日期／关系范围 | 成员历史、权重与受影响指标共同发布，不能新成员配旧指标 |
| 期货 | 合约、实约行情、映射、结算；产品＋交易日 | 必需输入整体校验；新增 FutureMarketPublication 一起发布，既有不可变快照不静默覆盖 |
| 商品 | 仓单、持仓、连续收益；来源／品种／合约＋日期范围 | 前置行情与映射完整后计算；空响应不证明应删除旧值，不改变现有滞后与 PIT 规则 |
| 利率、外汇与跨市场 | 曲线、FxDaily、基准；来源／序列／日期／期限 | 保留币种、时区、单位及可得时间；仅更新实际覆盖范围，缺失不填零 |
| 财报、财务指标与分红 | 报表版本与修正证据、FinaIndicator、Dividend；报告期或证券 | 稳定来源指纹去重，版本和证据一起发布，不删除历史版本或随意重建 ID |
| 宏观 | 序列、观察与发布日程；来源／序列／期间 | 保留 vintage、发布日期和定义；日程不等于已观测数据，部分响应不清空整段历史 |
| 代码归一与历史自愈 | 证券旧新代码对、交易日＋数据域 | 显式记录新增、修改和删除旧键；保留最早派生失效日，重试不能因缺口消失而跳过重算 |
| 派生指标与最终审计 | MarketIndicator、IndexIndicator、IndustryIndicator；受影响输出范围 | 使用完整滚动历史，原始与派生校验全部通过后才 ready；分年计算不代表分年发布 |

质量阈值、警告与错误分类、数据可得时间及来源完整性定义沿用各业务规则。审计失败只阻止候选发布，不触发主库维护门禁。

财报子进程先提交暂存单元，再报告父进程；父进程校验候选内容并保存断点后 ACK。父进程失踪则子进程退出。正式断点与候选写入不是同一事务，恢复时必须核对实物，不能仅看完成标记。

ETF 等数据覆盖需包含 registry 和活跃部署引用。准备时冻结需求指纹，发布前复查；新增依赖未覆盖时返回第一阶段补齐、重算和审计，期间不继续持有发布门禁。

## 5 原子发布

### 发布单元

每轮固定目标范围，一次正式事务发布。daily、weekly、repair 都可以细粒度保存断点，但不逐断点对外发布。重试不扩大原目标；新目标另开一轮。

这意味着 daily 中后一天准备失败时，整轮新候选暂不发布，不沿用当前“先发布成功日期前缀”的行为。若实测事务过大，需要重新讨论发布单元，不能临时分批提交却仍称整轮原子。

### 发布步骤

1. 第一阶段全部通过，关闭候选写连接与子进程，冻结候选及变更清单并校验哈希。
2. 进入第二阶段，取得发布意图锁停止接收新相关工作，再等待市场访问锁的已有共享持有者退出。排队 Job 不算在途执行；等待超时则解除本次门禁，不强行中断用户工作。
3. 在正式事务中核对 schema、baseDataRevision、依赖指纹及幂等发布身份。需要重新准备时退出并解除门禁。
4. 合并白名单内的市场变更、必要派生结果，更新水位与 dataRevision，保存发布凭据及待执行后续动作，一起提交。
5. 提交成功或确认回滚后，先释放市场访问排他锁，再释放发布意图锁和维护互斥锁，之后独立执行后续动作。提交结果不明时，以正式凭据判断是否已发布，禁止盲目重放。

事务内不下载、不调用 LLM／Python、不做耗时审计或发送通知。默认使用 Prisma 事务；吞吐及锁持有时间实测不满足要求时，再评审具体热路径。

### 合并边界

**复制到暂存库的范围是计算输入，不是回填范围。** 第一阶段生成并验证变更清单，包含 model、业务键、范围、增删改意图、行数和哈希；基线中未变化的记录不回填。

| 变更类型 | 正式事务中的回填方式 |
| --- | --- |
| 新交易日或新事实版本 | 按业务键／稳定来源身份插入新增记录 |
| 历史补缺 | 只插入缺失键，不覆盖已有记录 |
| 历史修订 | 按业务键更新明确变化的记录 |
| 完整切片替换 | 仅在证明来源完整后，删除并重写指定日期／证券范围，不扩大为整表替换 |
| 代码归一或明确删除 | 按清单删除旧键，并共同提交关联增改和受影响的派生结果 |

例如，暂存库为了计算读取十年行情，本轮只补缺 20 行、修订 3 行，就只回填这 23 行及受影响的派生结果。不能统一套用一种 upsert 或删除重建规则，空响应不证明范围应清空。

**禁止切换或覆盖整个正式数据库文件。** 用户、会话、研究、策略、任务、成交和账户记录不从候选复制回去，维护期间新增的用户数据必须保留。维护控制记录由正式协调器更新；不可变期货快照及同步证据遵循专属规则。

维护锁覆盖所有正式市场写入口，独立 sync／import／Signals 取数不能绕过发布协议。所有市场修改都要更新修订事实，否则只比较 dataRevision 无法发现基线变化。

发布排空需补齐当前 waitForRunningWork 未覆盖的普通 Research 执行和在途请求；发布后相关缓存／Python 会话按 dataRevision 失效，避免跨多次查询混用新旧数据。

## 6 发布后任务

| 任务 | 成功与失败规则 |
| --- | --- |
| Signals | 使用正式已发布数据及当前部署配置，按部署／交易日幂等生成；失败独立重试 |
| 账户结算 | 使用正式成交和账户，沿用修订／generation 校验；不从候选覆盖人工成交 |
| 因子气象 | 使用当前 pin、代码哈希、方法版本及数据修订；失败保留可追溯旧结果和错误 |
| 通知 | 结果提交后按业务身份去重发送；失败不回滚数据或记账 |

发布事务保存后续动作身份，进程提交后退出也能补执行。后续任务失败不覆盖市场发布成功事实，不阻塞主库。

现有 signal-only 流程仍包含市场修复与同步，改造时须将这些操作移入第一阶段，不能因名称而绕过候选协议。

## 7 故障恢复与清理

锁采用三个固定文件：维护互斥锁 M 全程防止两轮维护并行；第二阶段先持发布意图锁 P 排他阻止新工作，再持市场访问锁 R 排他完成回填。正常业务短暂取得 P 共享后取得 R 共享，释放 P 并持 R 到执行完成，消除“检查门禁后、登记执行前”的竞态。完整触发点、取锁顺序与恢复规则见 [维护锁设计](/Users/liucong/Projects/jixie/docs/design/maintenance-locking.md)。

状态查询仅供展示，业务准入必须实际加锁；不能只查 active 后执行。数据库 running／error、锁文件存在和心跳不是持锁证明。发布协调器独占正式事务连接，确认提交／回滚后释放门禁；子进程不得遗留持锁。异常恢复以真实句柄与正式发布凭据为准；部署故障、数据库不可用分别处理，不伪报成功，也不靠心跳超时强行解锁。

| 故障 | 处理与访问 |
| --- | --- |
| 准备阶段历史错误、下载／修复／审计失败或进程退出 | 保留错误和有效候选，原主库继续可用；按业务断点重试 |
| 快照或候选损坏 | 不使用无效断点，重建候选；不封站 |
| schema、规则或正式市场基线变化 | 旧候选失去发布资格，重新准备；可验证原始下载可复用，派生重算 |
| 发布等待超时或事务失败 | 未提交数据保持不变，解除本次门禁，稍后重试 |
| 发布提交前后进程退出 | 以正式发布凭据区分已提交和回滚；不能凭文件状态重复发布 |
| 发布成功、后续调度前退出 | 按持久化动作身份补调度，业务幂等 |
| 清理失败 | 记为待清理，不改变市场成功和访问状态 |
| 空间不足 | 停止新准备／发布尝试，保留可恢复信息，不自动删除唯一未完成候选 |

每个未完成目标保留一个当前可续跑候选。成功后关闭连接并清理暂存库及附件，正式库保留小型发布及审计摘要。失败保留期限、空间预算及剩余空间阈值在实施时依据真实库大小确定。

清理须确认无活动进程、目录归属及发布状态，绝不删除正式库、其 WAL 或锁文件。成功后的清理和失败后的断点恢复都不得依赖临时内存。

## 8 实施边界与验收

本轮实现涉及维护工作流与状态、发布协调器、暂存连接及 Worker、Signals／气象后续处理、CLI／部署脚本和维护状态 UI。运行是否进行、发布是否成功与 active 是否阻塞分别表示；第一阶段的任何错误都不得自动令 active 为 true。

移除独立 baseline 修复命令，将导入脚本、帮助和原调用方改接统一 repair；首次水位初始化入口保留。repair 的按需补缺与显式刷新行为需要统一实现，不能只改命令名称。独立 baseline 分支及实现已移除。

验收重点：

- 默认 repair 与显式区间共用协议；初始化水位不混入普通 repair。
- 第一阶段各故障点注入退出，主库市场数据不变、用户访问不中断，历史错误也不触发门禁。
- 按需复制包含计算及审计依赖，跨表来自同一读快照；用户业务表保持空表，缺依赖不回退主库。
- 各数据域的补缺、修订、删除、稳定 ID、不可变快照和范围外数据保持正确。
- 回填严格匹配已验证的变更清单，不写入仅用于计算的未变历史数据，不整表复制。
- 发布等待／事务／提交后分别中断，保证回滚或提交可判定，门禁不因遗留状态永久存在。
- 准备期间新增的用户数据不丢失，新增部署依赖重新检查，跨查询执行不混版本。
- 后续任务重复调度不重复产生业务副作用；失败不撤销发布、不封站。
- 测量快照空间与耗时、WAL 增长、最大修订事务、排空时间，并验证连接隔离、锁和文件权限。
