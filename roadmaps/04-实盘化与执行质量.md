# 04 · 实盘化与执行质量:深化主线五

## 问题陈述

主线五已规划「信号 → 半自动 → 自动」三阶段,方向正确。本文档补的是竞品对照后发现的三个薄弱点:
**缺模拟盘层、缺回测-实盘对齐的度量体系、缺元决策日志的产品化**。聚宽/米筐把模拟盘做成标配不是偶然——
它是「回测可信度」在时间维度上的延伸:回测证明历史上行得通,模拟盘证明**代码在真实时间流里行得通**
(数据晚到、停牌处理、信号生成 bug,只有真实跑起来才暴露)。

## 战略方向

### 方向一:模拟盘 = 主线五的免费副产品(强烈建议纳入 5.1)

关键洞察:jixie 的 5.1(信号生成)与模拟盘只差一步——信号生成出「明日应执行清单」后,
**次日收盘用真实行情按引擎同一套成交规则(开盘价、涨跌停、停牌、费税滑点)虚拟成交、记账**,
就是一个模拟盘。不需要盘中撮合(日频系统),不需要新引擎(成交逻辑就是现有 Portfolio 的),
只需要一张持仓/成交流水表和一个日终结算任务。

价值:策略上线前先模拟跑 1~3 个月,是「使用原则 3:小仓上线」的前置减险层,零真金成本验证
信号管道全链路;同时它天然产出 5.2 需要的「模型侧」净值序列。

技术方向:虚拟账户复用阶段二组合层的「子账户」模型(见 02,两者是同一张表的两种用途);
结算任务挂在每日信号 cron 之后;所有状态可从 SignalRun + 行情重放重建(幂等,坏了删掉重放)。

### 方向二:回测-实盘对齐仪表(阶段 2 的度量体系,提前设计)

5.2 说「回填实际成交价、积累对齐数据」,但没说**怎么看**。建议明确度量体系:

- **三条净值曲线**:回测重放(理论)/ 模拟盘(信号+虚拟成交)/ 真实账户(手工回填),两两之差各有含义:
  理论 vs 模拟 = 信号管道损耗(生成延迟、数据修正);模拟 vs 真实 = 执行损耗(滑点、手滑、拒绝执行);
- **逐笔偏差归因**:每笔信号标记终态——按价成交 / 偏价成交(记偏差 bp)/ 未执行(记原因:涨停买不进 /
  人为跳过 / 忘了),月度汇总「执行率」和「执行成本 bp」;**「人为跳过」次数是纪律的硬指标**,
  这是主线六「情绪的主战场在元层面」的可量化抓手;
- 积累 6 个月后,把实测执行成本 bp 反哺回测滑点参数(1.1 的参数闭环)。

### 方向三:决策日志产品化(使用原则 6 从 markdown 升级)

上线/下线/改参数/手动干预,现在靠人肉记 markdown。建议做成系统内的**只追加事件表**
(策略 id、事件类型、一句话理由、时间戳),在净值曲线上打标记点。工程量半天,
但把「元决策纪律」从自觉变成产品结构——回撤中翻看「上次我为什么下线它」比翻散落的 markdown 可靠。
不做审批流、不做复杂表单,一行字足矣(降低记录摩擦是这个功能成立的唯一前提)。

### 方向四:券商通道的现实路线(5.3 的战略预判,不加速执行)

调研维持 ROADMAP 判断:A 股个人程序化 ≈ QMT/miniQMT(Windows、常见 50 万门槛)或 PTrade(券商托管)。
补充两个战略观察:

- miniQMT 生态这两年第三方 Python 封装(xtquant 系)已相当成熟,「Windows VM 跑 adapter + 信号侧零改动」
  的形态可行性在上升;jixie 侧要做的只是 SignalItem 保持机读友好(已满足)+ 届时一个拉取信号的小客户端;
- **条件单先行**(5.2 已列):止损走券商条件单是零 API 成本的「半自动化」,优先级应高于任何 API 通道;
  通知渠道抽象(Notifier)建议把 Bark/Telegram 提前——邮件在手机上的到达率和时效性明显弱于推送,
  而信号系统的价值就在「当天收盘后一小时内看到」。

## 明确不做

- 盘中实时监控、盘中撤改单(日频系统无此需求);
- 多券商聚合、资管级风控(机构功能);
- 自动化通道在「模拟盘 + 手动执行 ≥6 个月、执行损耗已测量」之前不启动(先测量后自动化,
  否则自动化的是一个没校准过的系统)。

## 与既有规划的关系

- 方向一建议直接并入 5.1 的详设(`docs/design/daily-signals.md` 修订),它改变 5.1 的表结构设计;
- 方向二是 5.2 的验收标准来源;方向三独立小件,随时可做;方向四维持 5.3 💤 不变。
